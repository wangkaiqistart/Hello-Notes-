> **实施重点**：先用规格冻结目标和架构，再按 User Story 和依赖顺序实现；主体阶段可以用 Spec-Kit，增量阶段切换到轻量手工流程。

## 两阶段模式

### 主体阶段：Spec-Kit

1. 写项目宪章，固定关键工程原则。
2. 把需求转成五个 User Story：Provider、ReAct、Memory、Tool、Web Service。
3. 把技术方案转成实施计划和任务。
4. 按依赖顺序实现，并在每个阶段验证。

### 增量阶段：手工规格

主体架构稳定后，小改动不必重新跑完整流程。为每个变更写目标、范围、文件、验收和回滚，再让 AI 按任务执行。

## 协作规则

- 模块边界和公共接口先冻结。
- 并行任务必须拥有独立上下文和清晰文件范围。
- 每个任务完成后先做规格 Review，再做代码质量 Review。
- 测试、构建和运行证据必须进入交付记录。

## 五个 User Story 的依赖

Provider 提供模型调用，ReAct 依赖它完成循环，再接入 Memory 和 Tool；Web Service 将已验证的能力开放给调用方。CLI、Channel 和 Sandbox 为交互与执行提供支持。

[![AgentOS 能力依赖：Provider 接入模型，ReAct 组织循环，再集成 Memory、Tool、入口和执行环境](/images/ai-programming/notes/agentos-dependencies.svg)](/images/ai-programming/notes/agentos-dependencies.svg)

## 并行协作的前提

AI 能够并行初始化多个模块，但并行不等于可以共享未冻结的接口。先定义公共契约，再拆任务，才能避免上下文漂移和重复实现。

## 从“写代码”到“把事情做成”

传统开发的思考路径通常是：理解需求、设计方案、编写代码、调试问题。AI 编程改变的是执行路径和工作重心：

| 维度 | 传统开发 | AI 编程 |
| --- | --- | --- |
| 核心动作 | 亲自编写实现 | 设计边界并驾驭 AI 执行 |
| 思考重点 | 类、方法和实现细节 | 目标、拆解、约束和验证 |
| 人的职责 | 设计、编码、调试 | 做关键判断、定义规则、验收结果 |
| 交付证据 | 代码和提交 | 可运行结果、测试、审查和运行证据 |

代码仍然是产出物，但不再是唯一衡量标准。对 AgentOS 这类系统，更重要的是能否把目标拆成可执行的范围，让 AI 在边界内工作，并用客观证据判断是否完成。

## SDD、Harness 和 Loop 三种思维

拿到一个项目时，可以从三个角度分别想一遍：

| 思维 | 要回答的问题 | 在 AgentOS 中的落点 |
| --- | --- | --- |
| **SDD** | 需求要拆成哪些块？每块的规格和验收是什么？ | requirements、User Story、spec、tasks |
| **Harness** | AI 能做什么、不能做什么？怎么约束和检查？ | constitution、模块边界、编码规则、测试和 Review |
| **Loop** | 哪些步骤可以自动重复？每一轮在哪里检查和退出？ | 实施循环、测试循环、失败反馈和稳定检查点 |

这三个词描述的是思考角度，不是必须安装的三个工具。先把目标、边界和验收想清楚，再选择 Spec-Kit、OpenSpec 或轻量手工方式落地。

## 一条稳定的实施路径

AgentOS 的主体开发可以按下面的顺序推进：

1. **想清楚要做什么**：明确目标、非目标、用户角色、关键流程和验收标准。
2. **立好规范与边界**：冻结模块职责、公共接口、技术决策、权限和禁止事项。
3. **拆成可执行任务**：按 User Story 拆分，每个任务写清文件范围、前置条件、完成标准和回滚点。
4. **让 AI 在边界内执行**：一次只处理一个清晰任务，执行后立即运行适合的检查。
5. **由人验收和收口**：判断行为、证据和风险是否满足目标，再决定是否进入下一块。

执行可以交给 AI，目标、边界、关键技术选择和“什么算完成”仍由人负责。

## 工程准备：先把文档变成施工依据

已有文档不需要重写一遍，而要转换成 AI 可以稳定消费的输入：

| 已有材料 | 转换后的产物 | 作用 |
| --- | --- | --- |
| 业界调研、需求文档 | spec 或 User Story | 固定范围、角色、流程和验收 |
| 技术方案 | plan | 固定技术栈、模块职责、依赖和关键决策 |
| 设计目标与不可妥协原则 | constitution | 让每个任务都遵守公共约束 |
| 需求中的验收 Demo | User Story 验收标准 | 把“能做”变成可演示、可检查的结果 |

输入必须是最新版本。模块数量、接口边界或技术选型一旦过期，后续生成的计划和任务就会沿着错误结构展开。

在当前 AgentOS 文档中，可以按[需求与范围](./requirements/)、[架构与技术决策](./architecture/)、[核心模块](./modules/)和[验收与演进](./roadmap/)的顺序建立上下文，再进入具体任务。

## SDD 的三种落地方式

没有一种拆解工具适合所有变更，选择取决于项目阶段、改动规模和执行者对系统的熟悉程度：

| 方式 | 适用情况 | 主要特点 |
| --- | --- | --- |
| **Spec-Kit** | 从零开始、规模中等以上、需求和模块较清晰 | 规格、计划和任务结构完整，适合主体建设和方法训练 |
| **OpenSpec** | 已有系统的棕地改造、局部增量或需要描述 delta | 重点描述现状与变更差异，减少重复说明 |
| **轻量手工** | 熟悉技术栈的小改动或已经稳定的主体架构 | 直接写目标、范围、文件、验收和回滚，减少流程成本 |

课程以 Spec-Kit 作为主体开发示例，以 OpenSpec 和轻量手工作为对照。这个选择是课程场景的建议，不是每次 AgentOS 变更都必须执行的命令；当前仓库仍应根据任务范围和已有项目规则决定流程。

## 按 User Story 拆分 AgentOS

主体能力按依赖关系拆分，比按日期或代码目录拆分更容易控制范围：

| User Story | 核心能力 | 主要模块 | 依赖与验收 |
| --- | --- | --- | --- |
| US-1 | Provider：接入 LLM | provider、core、boot | 模型调用和错误传播可验证 |
| US-2 | ReAct：组织循环 | core、tool、channel-cli、cli | 能完成一次工具调用闭环 |
| US-3 | Memory：管理记忆 | memory | 跨轮次或跨会话记忆可验证 |
| US-4 | Tool：接入 Plugin/MCP | tool、core | 工具参数、权限和结果回填可验证 |
| US-5 | Web Service：对外开放 | web、storage、cli | REST 契约、状态和审计可验证 |

依赖关系可以理解为：US-1 先提供模型能力，US-2 在此基础上组织循环；US-3 和 US-4 在循环契约稳定后可以并行；US-5 最后把已经验证的能力开放给业务系统。CLI、Channel、Storage 和 Sandbox 是多个 User Story 共享的支撑边界，不应被拆成互相重复的核心能力。

每个 User Story 都应有一个可演示结果，并关联需求文档中的验收 Demo。这样可以避免“模块写完了”替代“能力跑通了”。

## 和 AI 协作的纪律

为了让主体开发不漂移、不跑偏、不中断，可以固定四条协作纪律：

- **防漂移**：每个 User Story 完成后，检查 spec、plan、tasks、代码和测试是否一致。
- **纠跑偏**：生成的代码违反 constitution 或已冻结的技术边界时，先纠正约束，再继续实现。
- **防断片**：切换任务或上下文丢失时，重新读取项目宪法、对应 spec、plan 和最近的验证结果。
- **可回退**：每个 User Story 保留可识别的稳定检查点，出现回归时能回到最近一次已验证状态。

课件建议每个 User Story 建立一次 Git 提交作为检查点；实际执行仍遵循仓库的分支和提交授权规则，本页不把提交动作视为自动授权。

## 节奏示例与验收

课程给出的四周节奏是一个能力依赖示例：

| 周期 | 重点能力 | 预期结果 |
| --- | --- | --- |
| 第 1 周 | Provider + ReAct | Chat 多轮、工具调用和最小循环闭环 |
| 第 2 周 | Memory + Tool | 记忆读写、内置 Tool 和 MCP 接入 |
| 第 3 周 | Web Service | Spring MVC、接口状态和业务集成 |
| 第 4 周 | 多 Agent 与收尾 | 多实例并存、跨重启验证、文档和演示收口 |

时间投入和每周边界需要根据真实进度调整，不能用课程排期代替项目验收。AgentOS 的验收仍应回到[验收与演进](./roadmap/)：模型调用、工具闭环、会话记忆、统一入口、权限、超时、错误和审计都要有可复核证据。

## 课程建议与项目边界

第 10 节和第 12 节中的“下一节”“现场安装”“按课程节奏推进”等内容属于教学流程；它们帮助理解方法，但不会自动变成当前项目的执行指令。具体实施时：

- 课程中的 OryxOS 统一按当前项目名称 AgentOS 理解。
- 课程里的模块数量、技术依赖和示例排期需要与当前仓库文档重新核对。
- Spec-Kit、OpenSpec 和轻量手工是可选工作方式，按变更类型选择。
- AI 负责在边界内执行，人负责方向、技术取舍、风险和最终验收。
