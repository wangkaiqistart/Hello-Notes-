  原理



原理 ③：产物长什么样
 specify init 生成 .specify/ 工作区——四个正式文件，跟代码一起版本管理。



 constitution.md       项目宪法：非协商原则（写一次定下来，全程不轻易改）




 spec.md               需求规格：user story + acceptance criteria + 功能边界




 plan.md               技术方案：技术栈选型、模块划分、关键技术决策




 tasks.md              任务清单：按 user story 分组、标好依赖与可并行


四个文件是「人和 AI 之间的契约」，也是项目决策的留底——可审查、可共享、可回溯。

  怎么用



怎么用 ①：安装与命令体系
 specify init 起手；命令以 /speckit. 前缀触发。



 6 个核心命令                               3 个可选命令
 必走的闭环                                 加强代码质量

 · constitution：写项目宪法                  · clarify：specify 后反问澄清模糊点
 · specify：需求 → spec（user story）       · analyze：implement 前查一致性（防漂移）
 · plan：spec + 宪法 → 技术方案               · checklist：自定义质量校验清单
 · tasks：plan → 有序任务列表                 · （taskstoissues：任务转 GitHub issues）
 · implement：按 tasks 生成代码




命令语法不用背——理解每个命令解决什么问题，跑一遍就熟。

怎么用



怎么用 ②：典型工作流
从初始化到 implement，一条不跳步的流水线。



     01                 02              03             04                   05

初始化 + 宪法        →    specify       →   plan   →      tasks       →    implement

 specify init       （可选 clarify）       技术方案       （可选 analyze）       + review & commit




没有跨阶段 shortcut，没有「凭感觉跳过 plan 直接写代码」。每个 task 写完人工 review 再 commit。

怎么用 ③：一条命令长什么样
 拿两个最关键的命令，看真实的输入和输出。



 /speckit.specify                      /speckit.tasks

 输入：一句话 / 一段粗略需求                       输入：spec.md + plan.md




 输出：spec.md（约 800 行）——背景、user story、   输出：tasks.md——几十个有序任务，按 user story
 acceptance criteria、非目标（明确说不做什么）      分组，标好依赖关系和可并行项




你只写第一份 spec、检查 plan、最后 review 代码；中间的拆任务和执行，AI 自动跑。

什么时候用


什么时候用：它是「重武器」
 强在强制完整流程、产出结构化 artifact；代价是流程开销大。



 适合                                  不适合
 威力巨大                                开销大于收益

 · greenfield 中到大型项目                 · 小 feature、单文件、快速原型
 · 需求清晰，上游有文档或决策                     · 大型 brownfield 改造（上下文超限）
 · 用 AI agent 做主体开发                  · 探索性研究（需求未定会返工）
 · 团队要学 SDD 工程方法论                    · 个人小实验（6+3 命令太重）




用在合适的场景威力巨大，用在不合适的场景就是负担——工具匹配工作性质。
