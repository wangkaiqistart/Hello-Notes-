这份指南解决一个实际问题：已经有需求、架构和技术决策后，如何把它们变成 AI 可以执行、团队可以复核、项目可以回退的实施过程。

AgentOS 当前是 JDK 21、Spring Boot 4.1.2、Spring AI 2.0.2 的 Maven 多模块骨架。本文使用当前项目的 9 个核心模块和五大能力作为事实基线；Spec-Kit 是否安装、具体命令是否变化，应以实施时采用的版本和仓库规则为准。

## 一、从“写代码”转向“把事情做成”

传统开发通常沿着“理解需求 → 设计方案 → 编写代码 → 调试问题”推进，人的主要执行动作是写代码。AI 协作开发把执行路径改成“明确目标 → 固定边界 → 让 AI 执行 → 人工验收”：代码仍是产出物，但人的重点转向拆解、约束、判断和验证。

| 维度     | 传统开发           | AI 协作开发                      |
| -------- | ------------------ | -------------------------------- |
| 核心动作 | 亲自编写实现       | 设计边界并让 AI 执行             |
| 思考重点 | 类、方法和实现细节 | 目标、拆解、约束和验收           |
| 人的职责 | 设计、编码、调试   | 做关键判断、定义规则、复核证据   |
| 交付证据 | 代码和提交         | 运行结果、测试、审查和回退检查点 |

变化的是路径和重心，需求、工程判断、计算机基础和最终责任仍然由人承担。AI 可以在边界内生成代码和运行检查，但不能替人决定范围、风险或“什么算完成”。

## 二、拿到项目先用三种思维拆一遍

SDD、Harness 和 Loop 是三个思考角度，不是必须同时安装的三个工具：

| 思维        | 要先回答的问题                         | AgentOS 中的落点                     |
| ----------- | -------------------------------------- | ------------------------------------ |
| **SDD**     | 需求要拆成哪些块？每块如何验收？       | 需求、User Story、spec、tasks        |
| **Harness** | AI 能做什么、不能做什么？如何检查？    | constitution、模块边界、质量门和权限 |
| **Loop**    | 哪些步骤可重复？每轮在哪里检查和退出？ | 实施循环、测试循环、失败反馈和检查点 |

一条稳定路径是：先明确要做什么，再固定规范和边界，然后让 AI 按任务执行，最后由人验收并收口。执行可以交给 AI，拆分方案、技术取舍、验收标准和风险判断不能交出去。

## 三、开发前先把项目变成施工依据

已有文档不需要重新改写成提示词，而要映射成 AI 可以持续读取的正式产物：

| 已有材料               | 实施产物                       | 固定的内容                       |
| ---------------------- | ------------------------------ | -------------------------------- |
| 业界调研和需求文档     | `spec.md`、User Story          | 范围、角色、流程、非目标和验收   |
| 技术方案               | `plan.md`                      | 技术栈、模块职责、依赖和关键决策 |
| 设计目标和不可妥协原则 | `constitution.md`              | 所有任务都必须遵守的工程约束     |
| 验收场景和演示要求     | User Story 验收标准和阶段 Demo | 可运行、可观察、可复核的完成条件 |
| 任务拆解和依赖关系     | `tasks.md`                     | 有序任务、前置条件和可并行边界   |

当前项目的阅读顺序建议是：[需求与范围](/projects/agent-os/requirements/) → [定位、架构与价值](/projects/agent-os/agent-os-positioning/) → [架构与技术决策](/projects/agent-os/architecture/) → [核心模块](/projects/agent-os/modules/) → [验收与演进](/projects/agent-os/roadmap/)。模块数量、技术选型和接口边界必须以最新版本为准；旧资料若写成 11 个模块，不能直接喂给计划生成工具。

## 四、工程准备：先对齐模块和公共边界

AgentOS 核心阶段包含 9 个 Maven 模块，五大核心能力由 `provider`、`core`、`memory`、`tool` 和 `web` 承载，`boot`、`cli`、`channel-cli` 和 `storage` 提供支撑：

| 模块                  | 主要职责                                             |
| --------------------- | ---------------------------------------------------- |
| `AgentOS-core`        | Profile、TurnContext、AgentService、ReActLoop 和编排 |
| `AgentOS-provider`    | 具名 ChatModel 映射、模型请求、重试和调用元数据      |
| `AgentOS-memory`      | MemoryService、SessionManager 和长期记忆后端         |
| `AgentOS-tool`        | ToolCallback、MCP Client、ToolRegistry 和 Sandbox    |
| `AgentOS-storage`     | PostgreSQL、JPA、Flyway、会话和审计持久化            |
| `AgentOS-web`         | REST 接入、响应规范、异常映射和接口文档              |
| `AgentOS-channel-cli` | 交互式对话渠道                                       |
| `AgentOS-cli`         | Picocli 命令入口和命令分发                           |
| `AgentOS-boot`        | 应用启动、依赖聚合和组件装配                         |

模块边界要先冻结，再拆任务。当前项目的关键边界包括：

- ReActLoop 自己驱动迭代，直接调用 Spring AI 2.0 的 `ChatModel`。
- 工具统一为 `ToolCallback`，由注入的 `ToolCallingManager` 执行，不能引入第二条自动执行路径。
- 会话和审计使用 PostgreSQL、JPA 与 Flyway，不使用 SQLite 或 H2 作为运行时事实源。
- `MemoryService` 统一会话记忆和长期记忆，不能让循环直接操作多个后端。
- 凭证由受控配置注入；工具权限、超时、结果截断、重试和审计必须在统一入口生效。

日志、指标、HTTP、API 规范、代码质量和依赖安全扫描属于共同地基。它们不是新的业务 User Story，却决定后续模块能否定位、验证和交付。

## 五、选择合适的规格化方式

没有一种工作流适合所有改动，选择取决于项目阶段、变更规模和团队对系统的熟悉程度：

| 方式             | 适用情况                               | 特点                               |
| ---------------- | -------------------------------------- | ---------------------------------- |
| **Spec-Kit**     | 从零开始、规模中等以上、需求和模块清晰 | 规格、计划和任务完整，适合主体建设 |
| **OpenSpec**     | 已有系统的棕地改造或描述局部 delta     | 聚焦现状与变更差异，减少重复说明   |
| **轻量手工规格** | 熟悉技术栈的小改动或稳定架构的增量任务 | 写目标、范围、文件、验收和回滚即可 |

AgentOS 的主体设计具备清晰需求、9 个模块和明确技术决策，适合采用规格化流程；已经稳定的增量改动则可以使用轻量手工规格。工具选择是工程判断，不能因为使用了某个 CLI 就跳过评审和验收。

## 六、Spec-Kit 的工作原理

Spec-Kit 是叠加在 AI Agent 之上的工作流层。它不替代 Claude Code、Copilot 或 Cursor，也不负责运行 AgentOS；它把需求、技术方案和任务组织成可版本管理的工程产物。

### 1. spec 是事实源

```text
spec.md  →  plan.md  →  tasks.md  →  code
需求规格     技术方案     任务清单      实现
```

`spec.md` 保存 user story、验收标准、功能边界和非目标；`plan.md` 固定技术选型、模块划分和关键决策；`tasks.md` 按 User Story 编排任务、依赖和并行关系。下游产物必须能追溯到上游规格，不能把聊天历史当作唯一依据。

### 2. 三个设计支柱

- **项目宪法**：把技术栈、模块边界、安全规则和不可妥协原则写成文件，每次生成和实现都引用它。
- **阶段闭环**：`specify → plan → tasks → implement`，前一阶段的正式产物是后一阶段的输入，不跳过关键审查。
- **一致性分析**：实现前或阶段完成后检查 `constitution`、`spec`、`plan`、`tasks`、代码和测试是否仍然一致，发现漂移先修正依据。

### 3. 产物目录

不同版本的 Spec-Kit 目录细节可能变化，当前应保持以下语义：

```text
.specify/
  memory/
    constitution.md
  specs/
    <feature>/
      spec.md
      plan.md
      tasks.md
```

产物应与代码一起版本管理，成为人和 AI 之间可审查、可共享、可回溯的契约。

## 七、准备阶段：先产出三类正式产物

### 1. constitution：先钉死不可妥协原则

AgentOS 的项目原则至少应覆盖：

1. JDK 21、Spring Boot 4.x、Spring AI 2.0.x 和 PostgreSQL 的版本边界。
2. 五大核心能力优先，治理扩展按阶段交付。
3. ReActLoop 自实现，Spring AI 负责模型和工具协议组件，不启用第二条工具执行循环。
4. 工具统一为 `ToolCallback`，执行经治理包装器并记录 `tool_invocations`。
5. `llm_calls`、工具调用、会话和轮次状态从核心阶段就保留可查询证据。
6. 不引入 SQLite/H2、厂商 SDK 或未经评审的新模块拆分。

宪法不是普通提示词。发现原则本身需要改变时，应暂停实施并由项目负责人重新讨论，不能让 AI 在执行任务时自行修改。

### 2. specify：把需求变成 User Story

输入是最新的需求文档和范围决策，输出是包含 user story、验收标准、非目标和边界的 `spec.md`。先人工确认范围，再进入计划阶段；不要把模糊需求直接交给实现任务。

### 3. plan：把方案变成模块化实施计划

输入是 `spec.md`、`constitution.md` 和当前技术方案，输出是模块职责、接口、依赖、关键决策和验证策略。人工 Review 至少要检查：Memory 是否被错误合进 Session、Tool 是否被拆成多个模块、Spring AI 是否被误配置为自动执行工具，以及计划是否仍与 9 个模块一致。

## 八、按 User Story 拆解，而不是按日期拆解

主体能力按依赖关系推进：

```text
US-1 Provider → US-2 ReAct → ┬→ US-3 Memory ─┐
                             └→ US-4 Tool   ─┴→ US-5 Web Service
```

[![AgentOS 五个 User Story 的依赖关系：Provider 先于 ReAct，Memory 和 Tool 可并行，最后由 Web Service 对外提供能力](/images/ai-programming/notes/agentos-dependencies.svg)](/images/ai-programming/notes/agentos-dependencies.svg)

_图示表达能力依赖和可并行边界，不代表各模块已经全部实现。_

| User Story | 核心能力          | 主要模块                     | 阶段验收                             |
| ---------- | ----------------- | ---------------------------- | ------------------------------------ |
| US-1       | Provider 接入 LLM | provider、core、boot         | 一次模型调用、配置映射和错误传播     |
| US-2       | ReAct 循环        | core、tool、channel-cli、cli | 工具请求、执行、回填和终止闭环       |
| US-3       | Memory 记忆       | memory                       | 跨轮次或跨会话记忆可读写             |
| US-4       | Plugin Tool       | tool、core                   | ToolCallback、权限、超时和审计可验证 |
| US-5       | Web Service       | web、storage、cli            | REST 契约、状态、错误和审计可追踪    |

US-3 和 US-4 只有在 ReAct 的公共契约稳定后才适合并行。每个 User Story 都要有阶段 Demo，但阶段 Demo 不是最终发布条件；完整验收仍按[验收与演进](/projects/agent-os/roadmap/)执行。

## 九、和 AI 协作的四条纪律

| 纪律       | 做法                                                               |
| ---------- | ------------------------------------------------------------------ |
| **防漂移** | 每个 User Story 后检查 `spec`、`plan`、`tasks`、代码和测试是否一致 |
| **纠跑偏** | 代码违反 constitution 或已冻结决策时，先重读约束并修正方向         |
| **防断片** | 切换任务或上下文丢失时，重新读取宪法、对应规格和最近验证结果       |
| **可回退** | 每个 User Story 建立已验证检查点，出现回归时回到最近稳定状态       |

一次只交给 AI 一个边界清楚的任务。任务完成后立即运行适合的检查，不能让多个未验收任务堆在同一工作区里。

## 十、节奏和验收

能力依赖可以用四个阶段安排，但时间不是固定承诺：

| 阶段 | 重点能力         | 可观察结果                                |
| ---- | ---------------- | ----------------------------------------- |
| 1    | Provider + ReAct | 多轮对话、工具调用和最小循环闭环          |
| 2    | Memory + Tool    | 记忆读写、内置工具和 MCP 接入             |
| 3    | Web Service      | Spring MVC 接口、状态和业务集成           |
| 4    | 多 Agent 与收尾  | 多 Agent 并存、跨重启验证、文档和运维收口 |

最终验收要证明模型调用、工具闭环、会话记忆、统一入口、权限、超时、错误和审计都能被复核。通过编译、展示截图或返回一段合理文本，都不能单独代替运行证据。
