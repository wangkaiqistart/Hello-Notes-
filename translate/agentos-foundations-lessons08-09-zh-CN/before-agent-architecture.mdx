> **本页定位**：把一个 Agent 拆成五个组件和一个循环，再说明 AgentOS 为什么需要在单个 Agent 之上提供进程、隔离、治理和观测能力。这里整理的是架构理解，不把课件中的示例任务直接当成项目需求。

## 一句话模型

Agent 可以抽象为：

~~~text
Agent = LLM + Tools + Memory + Loop + Environment
~~~

这五个部分分别承担决策、行动、状态、持续执行和现实交互。LLM 让 Agent 更容易实现，但 Agent 这一类程序并不从 LLM 才开始；强化学习系统、游戏 NPC 和自动化控制程序也可以具备感知、决策、行动和反馈循环。

单次调用模型更接近 chatbot：输入一次，返回一次。只有把模型放入可持续运行的循环，让它根据工具结果和环境变化继续决定下一步，系统才具备 Agent 的执行特征。

## 五个组件在 AgentOS 中各自负责什么

| 组件 | Agent 中的职责 | AgentOS 的承载关系 |
| --- | --- | --- |
| **LLM** | 读取目标和当前状态，决定下一步行动，解释工具结果 | AgentOS-provider 负责 Provider 到 ChatModel 的映射；模型只产生回答或结构化工具调用意图 |
| **Tools** | 读写文件、访问网络、查询数据库或调用远程服务 | AgentOS-tool 统一 ToolCallback、参数校验、超时、结果截断、权限和审计 |
| **Memory** | 保存当前上下文、任务进度、工具结果和跨会话事实 | AgentOS-memory 区分 Session 消息与长期记忆，由上下文构建器决定本轮注入内容 |
| **Loop** | 反复执行“思考 → 行动 → 观察”，直到完成或停止 | AgentOS-core 中的 ReAct 运行时负责迭代、终止、错误反馈和轮次状态 |
| **Environment** | 提供 Agent 能感知和改变的世界，同时定义能力边界 | 工作区、文件系统、网络、数据库、用户入口和 Sandbox 共同构成受控运行环境 |

这张表描述的是职责边界。一个组件可以有多个实现，但不应因为更换模型、工具或存储后就把所有逻辑重新塞回循环。

## Loop 是 Agent 的灵魂

ReAct 循环可以写成四步：

1. **Reasoning**：模型根据目标、Memory 和当前 Observation 判断下一步。
2. **Acting**：运行时执行模型提出的 Tool 调用。
3. **Observation**：运行时把工具结果、错误或环境变化整理成新的观察结果。
4. **继续或结束**：把新状态交回模型，直到任务完成或触发停止条件。

概念上的循环如下：

~~~java
while (!finished && steps < maxSteps) {
    // 读取当前受控环境状态和会话上下文
    Observation observation = environment.observe(memory);

    // 模型只做决策，可能返回最终回答或结构化工具调用
    Decision decision = llm.decide(observation, memory);

    if (decision.hasToolCall()) {
        // 由统一执行入口校验并执行工具，再把结果写回上下文
        ToolResult result = toolExecutor.execute(decision.toolCall());
        memory.append(observation, decision, result);
    } else {
        // 没有工具调用时，通常可以形成最终回答
        finished = decision.isFinalAnswer();
        memory.append(observation, decision, null);
    }

    steps++;
}
~~~

这段代码表达的是运行机制，不是某个框架的可直接复制实现。AgentOS 需要额外管理四类循环控制：

- **停止条件**：任务完成、没有新的工具调用、达到最大迭代次数，或用户主动中断。
- **错误恢复**：工具失败后根据策略重试、降级、把错误反馈给模型，或结束本轮。
- **上下文压缩**：历史过长时按轮次裁剪或压缩，保留仍会影响决策的事实。
- **模型路由**：规划、执行后总结和评估可以选择不同模型，但路由规则必须可观测、可配置。

因此，循环的复杂度不只来自 while。终止、超时、并发、失败反馈和状态持久化决定了它能否稳定运行。

## 用一个任务看清五组件如何协作

以“读取 README，翻译成中文，写入 README.zh.md”为例：

| 轮次 | LLM 的决定 | Tool 与 Environment | Memory 中新增的状态 |
| --- | --- | --- | --- |
| 1 | 先读取原文件 | read_file 访问受控工作区 | 原任务和文件内容 |
| 2 | 根据已读内容完成翻译 | 这一轮可以只生成中间结果 | 翻译草稿和当前进度 |
| 3 | 写入目标文件 | write_file 修改受控工作区 | 写入结果或错误 |
| 4 | 检查结果并结束 | 不再调用工具 | 完成状态和最终响应 |

五个组件一个都不能省：LLM 负责决策，Tools 负责行动，Memory 保存过程，Loop 推动下一轮，Environment 提供实际对象和约束。

## LLM 与 Tools 的边界

模型不会直接打开文件、访问数据库或发送 HTTP 请求。模型先生成包含工具名称和参数的结构化调用意图，运行时再负责：

1. 检查工具是否在当前 Agent 的允许集合中。
2. 校验参数、权限、超时和幂等策略。
3. 执行工具并记录结果、错误和审计信息。
4. 把结果转成下一轮模型可以理解的 Observation。

这条边界决定了 Agent 的能力上限和风险上限：工具越多，Agent 能做的事越多；权限越宽，错误副作用也越大。MCP 的价值在于把远程能力包装成可发现、可插拔的工具，但它不会自动替代权限、超时和审计设计。

在 AgentOS 中，Provider 不执行工具，ReAct Loop 不直接承载每个工具的业务逻辑，所有工具都应经过统一的执行入口。这样 CLI、Web Service 和定时触发才能共享同一套治理规则。

## Memory 不是“把全部历史塞进 Prompt”

Memory 至少分为两种作用域：

- **短期记忆**：当前 Session 的消息、任务进度、工具调用和结果，服务于本轮连续推理。
- **长期记忆**：跨 Session 的用户偏好、项目背景、关键决策和经验，服务于后续请求的检索和复用。

没有长期记忆的系统仍然可以是 Agent，只是每次会话都从零开始。长期记忆也不等于无条件加载所有历史；写入前要筛选，读取时要按当前任务检索，超过上下文上限时要截断或压缩。

对应到 AgentOS：

- Session 存储保证同一会话的上下文和工具结果可恢复。
- Memory Service 对外提供统一门面，隐藏文件、数据库或向量后端的差异。
- 上下文构建器控制哪些短期消息、摘要和长期记忆进入本轮 Prompt。
- 记忆写回要有明确策略，不能把模型的每句输出都当成稳定事实。

## Environment 决定能力上限，也承载安全底线

Environment 是 Agent 所处的“世界”，常见组成包括：

- 文件系统和工作区；
- 网络和可访问的 URL；
- 数据库及可查询的表；
- CLI、Web、IM 或 API 等用户入口；
- 运行时配置、凭证和其他外部服务。

判断一个能力能否安全开放，至少要回答三个问题：

1. 这个能力是否有稳定的 API 或 SDK，可以被工具化？
2. 谁可以调用，允许访问哪些路径、命令、域名和数据？
3. 产生副作用后能否回滚、重试、撤销或交给人工确认？

Sandbox 是 Environment 的安全设计，不只是一个工作目录。它应把路径、命令、网络、资源和凭证边界落成可检查的策略，让一个 Agent 即使执行失败，也不会影响无关工作区或其他 Agent。

## 如何判断“它是不是 Agent”

| 对象 | 是否足以称为 Agent | 判断依据 |
| --- | --- | --- |
| LLM | 不足 | 它是决策组件，没有工具、环境和持续执行能力 |
| 单轮 chatbot | 通常不足 | 没有根据反馈继续决策的自主循环 |
| 固定 Workflow | 不一定 | 路径完全预定义时，它更接近确定性编排；其中可以嵌入 Agent |
| Agent | 可以 | 存在基于状态自主选择下一步的循环，并能通过工具作用于环境 |

判断一个系统时，先问它是否能自主决定下一步，再检查 Tools、Memory、Loop 和 Environment 的边界，而不是只看产品名称。

## 从一个 Agent 到 AgentOS

单个 Agent 是一个应用实例；AgentOS 是承载多个 Agent 的运行时底座。两者的差异在于是否需要管理共享能力和系统级约束：

| 单个 Agent | AgentOS |
| --- | --- |
| 关注一次任务能否完成 | 关注很多 Agent 能否稳定运行 |
| 一个上下文和一组工具 | 多 Agent 的会话、工作区和工具隔离 |
| 手动配置一个模型 | Provider 映射、模型路由和成本控制 |
| 出错后人工查看日志 | 统一的状态、指标、调用审计和故障定位 |
| 直接使用本地能力 | Sandbox、权限、超时、重试和副作用治理 |
| 进程生命周期由应用负责 | 负责 Agent 的启动、停止、重启和定时触发 |

因此，AgentOS 的重点不是再造一个聊天页面，而是把 Agent 的公共运行能力沉淀成可复用、可审计、可替换的基础设施。项目中的 [架构与技术决策](./architecture/)、[核心模块](./modules/) 和 [验收与演进](./roadmap/) 分别回答分层、实现顺序和验收证据问题。

## 工程结论

1. **先画边界，再选实现**：先定义 Provider、Tool、Memory、Loop 和 Environment 的职责，再决定使用哪种模型、存储和工具框架。
2. **把循环当作核心产品能力**：最大迭代次数、超时、错误反馈、上下文压缩和并发控制都属于 Agent 的基本能力。
3. **先治理工具和环境**：限制工具集合、路径、命令、网络和凭证，比单纯增加模型能力更能决定系统是否可上线。
4. **把记忆写入和读取分开设计**：会话历史、摘要和长期事实有不同生命周期，不能用一个无限增长的消息列表代替。
5. **用运行证据验收**：编译通过或模型返回一段合理文本，都不能证明循环、工具、记忆和隔离真的工作；需要用测试、日志、审计记录和失败案例验证。
