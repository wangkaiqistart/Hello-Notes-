Agent 是根据目标和环境反馈选择下一步行动的程序。理解它，可以从五个部分入手：**LLM 决策、Tools 行动、Memory 保存状态、Loop 推进任务、Environment 提供交互对象与约束。**

这是一种架构拆解方式。Agent 不限于语言模型系统，也不一定需要跨会话的长期记忆；这里关注以模型驱动工具调用的 Agent，以及它在 AgentOS 中的运行方式。

## 五个组件分别负责什么

```text
Agent = LLM + Tools + Memory + Loop + Environment
```

| 组件            | 解决的问题                                   | AgentOS 的职责映射                                                  |
| --------------- | -------------------------------------------- | ------------------------------------------------------------------- |
| **LLM**         | 根据任务和已有信息，选择工具或形成回答       | ProviderService 按名称选择 ChatModel，返回 ChatResponse             |
| **Tools**       | 读文件、请求服务、查询业务数据、执行受控操作 | ToolRegistry 管理 ToolCallback；ToolExecutor 统一发起执行           |
| **Memory**      | 保存会话过程，并按需复用跨会话事实           | MemoryService 汇集会话记忆与长期记忆，交给 PromptBuilder 组装上下文 |
| **Loop**        | 根据模型与工具结果继续、结束或中断           | ReActLoop 管理迭代，AgentService 协调轮次状态与会话                 |
| **Environment** | 定义可以接触哪些文件、网络、系统和用户入口   | 工作区、外部服务、凭证及 Sandbox 共同形成运行边界                   |

模型通过工具作用于环境，观察结果回到上下文，再影响下一次决策。五个组件的关系如下：

## 先分清会话、轮次和迭代

这三个概念决定状态怎么保存、上限怎么计算：

| 概念                | 边界                                   | 例子                             |
| ------------------- | -------------------------------------- | -------------------------------- |
| **Session：会话**   | 一段连续对话，包含多个轮次             | 用户持续向运维助手提问           |
| **Turn：轮次**      | 一条用户消息进入，到最终回答或异常终止 | “检查服务状态并给出建议”         |
| **Iteration：迭代** | 一次模型推理及其后续工具处理           | 模型要求查状态，工具返回查询结果 |

一个轮次可以包含多次迭代，一次模型响应也可以提出多个工具调用。限制模型迭代数，不能代替限制工具调用总数。

Agent 定义位于 `.AgentOS/agents/<name>/AGENT.md`：frontmatter 派生 Profile，决定使用哪个 provider、model 和工具集合；正文提供任务指令。全局连接在 `application.yaml`，聊天模型由 Agent 显式选择，具体配置见 [Provider 原理与实现](/projects/agent-os/provider/)。

## Loop 如何把组件串起来

ReAct 表达的是“根据当前信息决策 → 执行动作 → 读取结果 → 再决策”。不需要把模型的内部推理过程输出成日志；运行时关注的是实际响应、工具请求、工具结果和结束状态。

AgentOS 的主链路按以下顺序组织：

1. **开始轮次**：确认 Agent 和会话，取得会话租约，创建轮次记录与截止时间。
2. **构造 Prompt**：组合 Agent 指令、Bootstrap、Skill 元数据、长期记忆、近期完整轮次和当前用户消息；工具定义放在请求选项中。
3. **请求模型**：ProviderService 选择 ChatModel，完成一次模型请求并记录调用审计。
4. **判断输出**：没有工具调用时，保存助手消息并结束；有工具调用时，交给 ToolExecutor。
5. **执行并回填**：ToolExecutor 调用注入的 `ToolCallingManager.executeToolCalls(prompt, response)`，获取工具结果及完整历史。
6. **继续或结束**：`returnDirect()` 为 true 时直接返回；否则以 `conversationHistory()` 继续下一次模型请求。达到迭代上限、超时、取消或租约失效时终止。

`conversationHistory()` 已包含原消息、助手的工具请求和工具响应，不应再手工重复追加同一组消息。若一次响应调用了多个工具，只有它们全部声明直接返回时，`returnDirect()` 才为 true。

### 两道上限与四类超时

| 控制项                     | 约束对象                                           |
| -------------------------- | -------------------------------------------------- |
| `settings.max_iterations`  | 一个轮次最多进行多少次模型推理                     |
| `spring.ai.tools.limits.*` | 一个轮次内单工具和工具总调用次数                   |
| Provider 超时              | 一次模型请求                                       |
| 工具超时                   | 一次工具操作，需要在 HTTP、子进程或 MCP I/O 层生效 |
| `settings.turn_timeout`    | 整个轮次的执行预算                                 |
| HTTP 同步等待时间          | 接口等待结果的时间，不等于轮次执行时间             |

HTTP 同步等待到期后可以返回 `202` 和轮次标识，让后台继续执行；这不代表任务失败，也不代表可以取消已产生副作用的操作。同一会话已有执行中的轮次时，应拒绝并发进入，而不是让两条消息同时修改同一段历史。

流式调用先聚合完整的工具请求，再执行工具；不能把半段 JSON 参数直接传给工具，也不能在已经输出文本增量后无条件重放模型请求。

## 用文件翻译任务走一遍

目标是“读取 README，翻译成中文，写入 README.zh.md”。假设文件工具已经注册，且输入、输出路径都在允许范围内，一条可能的执行路径是：

| 迭代 | 模型返回什么                              | 运行时做什么           | 新增上下文             |
| ---- | ----------------------------------------- | ---------------------- | ---------------------- |
| 1    | 请求 `read_file` 读取原文                 | 校验路径，读取文件     | 助手工具请求与原文结果 |
| 2    | 请求 `write_file`，参数包含译文和目标路径 | 校验路径并写入文件     | 助手工具请求与写入结果 |
| 3    | 返回完成说明，不再请求工具                | 保存助手消息，结束轮次 | 最终回答               |

翻译可以在生成 `write_file` 参数时完成，不需要单独安排一次只返回草稿的模型调用。按这里的循环规则，模型一旦返回没有工具调用的普通回答，本轮通常就结束了。

如果任务要求验证文件内容，可以在写入后再请求读取核对；实际迭代次数由任务与模型响应决定。写入失败应反馈错误，不能只凭模型说“已完成”就判定成功。

## 模型与工具的边界

`ChatModel.call(Prompt)` 和 `stream(Prompt)` 只返回模型响应，不自动执行其中的工具请求。AgentOS 主链路由 ReActLoop 驱动，工具只经 ToolExecutor 调用统一注入的 ToolCallingManager 执行。

工具来源可以不同，但执行治理应一致：

- 本地 `@Tool` 方法和显式声明的回调统一为 ToolCallback。
- MCP 工具通过适配器转换为 ToolCallback。
- 注册表中的回调由 GovernedToolCallback 包装，处理截止时间、超时、幂等重试、结果截断、脱敏和审计。
- 内置工具在实际 I/O 前调用 Sandbox，检查路径、命令或目标端点。

ToolContext 用于传递 TurnContext 等应用数据，不应放进模型消息或工具 Schema；转发到 MCP 时还需去掉内部上下文。辅助 ChatClient 不携带工具，避免出现另一条工具执行路径。

Skill 则是另一类输入：它提供方法、脚本和参考材料。ContextLoader 先注入可见 Skill 的名称、说明和路径，正文由模型通过 `read_file` 按需读取。**Skill 不是 Tool，也不会因为写进文档就自动获得执行权限。**

## Memory：持久化记录与当前上下文分开

完整记录回答“发生过什么”，模型上下文回答“这次需要知道什么”，长期记忆回答“以后值得记住什么”。三者可以共享事实，但生命周期不同。

| 数据             | 保存方式与用途                                                                                | 上下文策略                                    |
| ---------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 会话、轮次和消息 | PostgreSQL 中的 `sessions`、`agent_turns`、`session_messages`                                 | 按完整轮次选择近期历史，兼顾轮数和 token 预算 |
| 长期记忆         | LongTermMemoryStore；默认 `.AgentOS/memory/MEMORY.md`，另有 PostgreSQL 与自托管 Mem0 后端设计 | 核心区全量，归档区按预算加载或检索            |
| 情景记忆         | 跨任务积累经验与过程知识                                                                      | 后续扩展，不等同于已经落库的会话消息          |

MemoryService 提供统一门面，内部委托 SessionManager 和 LongTermMemoryStore。模型上下文窗口不是数据库；从 Prompt 中裁掉旧消息，不意味着删除持久化历史。

裁剪时保留完整的助手工具请求与对应结果，失败轮次要避免带入悬空的工具请求。长期记忆通过 `save_memory` 写入，使用 `recall_memory` 检索；不把每句模型输出都自动认定为稳定事实。

当前长期记忆设计包含核心区与归档区，核心区不参与截断。默认文件属于工作区级资源，不能仅凭不同的 Agent 名称就推断长期记忆已按用户或租户隔离。向量索引用于召回，不代替记忆本体的持久化。

## Environment：工具能到哪里，系统就要约束到哪里

Environment 包括文件系统、网络、业务服务、用户入口与运行凭证。工具集合决定“能做什么”，环境策略决定“能对谁、在哪里做”。

| 对象     | 必须明确的边界                                         |
| -------- | ------------------------------------------------------ |
| 文件     | 允许路径、真实路径与符号链接、读写范围                 |
| 网络     | 允许的域名和端点、连接与读取超时                       |
| Shell    | 可执行命令、参数、进程时限；解释器可绕过哪些应用层限制 |
| 凭证     | 由应用注入，不交给模型，不进入日志与工具结果           |
| 远程 MCP | 工具暴露范围、服务端权限、请求超时及内部上下文过滤     |

WhitelistSandbox 是应用层校验，不能等同于操作系统或容器隔离。MCP 工具在远端执行，也不会自动受到本地文件与命令白名单保护。运行不可信代码或服务多租户，需要更强的独立执行边界。

重试同样属于环境治理：只对已确认幂等且满足策略的工具自动重试；写文件、通知或提交业务数据等操作发生超时后，必须考虑副作用可能已经完成，不能把“没有收到结果”当成“没有执行”。

## 从单个 Agent 到运行底座

单个 Agent 关心任务目标；AgentOS 将多个 Agent 共用的模型接入、会话、工具、调度和审计沉淀为运行底座。这里的“OS”是应用层类比：一个进程可以承载多个 Agent 定义，不要求为每个 Agent 启动独立系统进程。

当前项目已有多模块骨架、启动与 API 规范、日志及架构检查基线；上述 Provider、循环、记忆、工具和业务持久化链路仍需逐项实现与验收。

验收至少覆盖：工具确实执行且没有重复执行，结果可回填，超限与取消能停止，消息可读回，失败可追溯，越界操作被拒绝。模型生成合理回答、类能编译或应用能启动，都不能单独证明这些行为成立。
