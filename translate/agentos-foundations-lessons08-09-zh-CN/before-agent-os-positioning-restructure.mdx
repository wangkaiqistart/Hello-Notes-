AgentOS 面向需要私有部署、复用 Java 服务并追踪执行过程的团队，目标是让多个业务 Agent 共用一套运行底座：**一个目录定义一个 Agent，一个进程承载多个 Agent。**

平台统一处理模型接入、循环执行、会话、记忆、工具和审计；业务方定义目标、规则、知识和可用能力。企业级治理是建设目标，需要按阶段落实，不能由“私有部署”或“Agent OS”这个名称推导出来。

## Agent、Runtime 与 Agent OS

| 层次         | 关注的问题                        | 主要内容                                             |
| ------------ | --------------------------------- | ---------------------------------------------------- |
| **Agent**    | 这个业务任务要做什么              | 任务指令、模型选择、工具集合与领域知识               |
| **Runtime**  | 一次任务怎样执行                  | 组装上下文、调用模型、执行工具、更新状态、判断终止   |
| **Agent OS** | 多个 Agent 怎样共用服务并受到管理 | Agent 注册、入口适配、共享接入、会话管理、调度与治理 |

AgentOS 是用户态应用，并不接管内核调度，也不要求每个 Agent 对应一个操作系统进程。Agent 的注册与注销、轮次的开始与取消、宿主应用的启动与关闭，是三种不同的生命周期。

与相邻产品的分工也应明确：

- **模型 SDK 或框架**提供模型、工具与消息等基础接口，AgentOS 在其上提供完整运行链路。
- **Workflow 平台**适合把确定步骤组织为流程，也可以把 AgentOS 作为可调用的任务执行服务。
- **业务 Agent**面向客服、运维、研发或知识管理等具体目标，复用底座而保留业务权限与验收规则。

选择哪一层，取决于是否需要动态决策、是否有明确业务流程，以及是否需要多个 Agent 共享运行能力。简单任务不必先建设完整平台。

## 企业需求要落成可检查的边界

AgentOS 的定位可以归纳为统一、私有、易接入、可观测。它们分别对应不同的工程要求：

| 定位       | 要证明什么                                   | 不能直接推断什么                                |
| ---------- | -------------------------------------------- | ----------------------------------------------- |
| **统一**   | 不同入口复用 AgentService 和同一条运行链路   | 所有 Agent 自动拥有相同权限或可以共享全部数据   |
| **私有**   | 部署、存储、网络出口和凭证由企业控制         | 应用部署在内网，就不会向外部模型或 MCP 发送数据 |
| **易接入** | 新业务优先复用 Agent 定义、Skill 与已有 Tool | 只写一段提示词就能跳过接口开发、权限和业务验收  |
| **可观测** | 轮次、模型与工具记录能关联，失败原因可追溯   | 有控制台日志，就已经具备完整审计或成本账单      |

如果要求数据不出域，模型、Embedding、MCP、工具下游与日志出口都要在允许边界内。使用外部 API 时，应明确发送哪些数据；部署位置与数据流向需要分别确认。

审计也需要分层：执行记录回答“发生了什么”，查询与报表回答“如何查”，访问控制、留存策略和防篡改机制回答“证据由谁保护”。写入两张审计表只是基础，不能替代后面的治理要求。

## 业务方如何定义一个 Agent

Agent 定义采用目录结构，frontmatter 提供运行配置，正文描述业务任务。Skill、脚本和参考资料按需放在目录中；下面是组织方式示意，不是当前可执行命令。

```text
.AgentOS/
  agents/
    ops-agent/
      AGENT.md          # frontmatter 派生 Profile，正文是任务指令
      skills/           # 指向公共 Skill 的相对软链接
      scripts/          # 可选脚本
      REFERENCE.md      # 可选参考
  skills/               # 公共 Skill
  memory/MEMORY.md      # 默认长期记忆文件
  mcp_servers.yaml      # MCP 服务配置
```

全局模型连接放在 `application.yaml`；每个 Agent 显式选择 provider、聊天模型与工具，不靠全局默认模型决定业务行为。AgentLoader 负责校验和派生 Profile，ContextLoader 负责加载任务指令、Bootstrap 与可见 Skill 的元数据。

这几种对象作用不同：

| 对象           | 业务方提供什么                   | 底座负责什么                                       |
| -------------- | -------------------------------- | -------------------------------------------------- |
| **Agent 定义** | 目标、约束、模型、工具与触发规则 | 配置校验、Profile 索引、上下文构建与执行           |
| **Skill**      | 可复用的方法、脚本和参考资料     | 发现绑定关系，先展示元数据，再按需读取正文         |
| **Tool**       | 可调用的业务能力及参数契约       | 注册、权限过滤、执行、超时、结果处理和审计         |
| **MCP 服务**   | 通过协议暴露的远程工具           | 连接、发现与回调适配；服务端仍负责自己的权限与隔离 |

Skill 不能替代真实接口，MCP 也不会自动赋予企业系统访问权限。业务方仍要提供可靠的工具实现、账户权限、数据口径与验收题集。

## 四层架构：入口、引擎、能力、支撑

CLI、REST 与定时触发都汇入 AgentService；引擎协调 Provider、Memory 和 Tool，底层保存状态、加载定义并约束操作。四层是职责视图，不等于四个 Maven 模块，也不是所有请求都逐层向下走一遍。

| 层             | 职责                                       | 主要组成                                                            |
| -------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| **入口与触发** | 接受消息或定时事件，返回结果与状态         | CliChannel、REST、AgentScheduler                                    |
| **运行引擎**   | 管理轮次，构造上下文，推进决策与执行       | AgentService、ReActLoop、PromptBuilder、ToolExecutor                |
| **可替换能力** | 对接模型、会话与长期记忆、本地和远程工具   | ProviderService、MemoryService、ToolRegistry、MCP Client            |
| **支撑设施**   | 加载配置、保存状态、约束 I/O、记录调用过程 | AgentLoader、ContextLoader、PostgreSQL、Flyway、Sandbox、日志与审计 |

### 与现有工程模块对应

项目根 POM 已声明九个模块，职责按以下边界展开：

| 模块                  | 职责                                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| `AgentOS-core`        | Profile、TurnContext 等核心契约，AgentService、ReActLoop、PromptBuilder、ToolExecutor、加载与调度编排 |
| `AgentOS-provider`    | 具名 ChatModel 映射、模型请求、重试与元数据，独立 EmbeddingModel                                      |
| `AgentOS-memory`      | MemoryService、SessionManager、LongTermMemoryStore 和记忆工具                                         |
| `AgentOS-tool`        | 内置工具、MCP Client、ToolRegistry、GovernedToolCallback 和 Sandbox                                   |
| `AgentOS-storage`     | PostgreSQL 数据源、会话及审计持久化、Flyway 迁移与任务锁存储                                          |
| `AgentOS-web`         | REST 接入、响应规范、异常映射和接口文档                                                               |
| `AgentOS-channel-cli` | 交互式对话渠道                                                                                        |
| `AgentOS-cli`         | Picocli 命令入口、配置与命令分发                                                                      |
| `AgentOS-boot`        | 应用启动、依赖聚合和组件装配                                                                          |

ToolExecutor 属于核心编排，GovernedToolCallback 与具体工具属于工具模块；它们不能因为名字接近就放进同一个业务实现类。契约与实现分开，核心模块不反向依赖具体适配器。

Java 21 与虚拟线程适合保留同步调用结构，并复用已有服务与运维体系。但虚拟线程不增加数据库连接数、模型配额或下游容量，仍需并发限制、超时和容量测试。

## 五项核心能力怎样协作

| 能力            | 必须建立的契约                                                                 |
| --------------- | ------------------------------------------------------------------------------ |
| **Provider**    | 按 provider 名称显式选择连接，使用完整请求选项，返回原始模型响应，记录每次尝试 |
| **ReAct**       | 自行控制迭代、工具反馈、终止条件与轮次状态                                     |
| **Memory**      | 区分完整会话记录、本轮上下文与长期事实，控制加载预算                           |
| **Tool**        | 统一回调与执行入口，处理权限、I/O 超时、幂等性、脱敏和审计                     |
| **Web Service** | 向业务系统提供会话与 Agent 调用接口，明确同步等待和后台轮次的关系              |

CLI 和定时任务是复用这些能力的入口，不是另写一套执行引擎。通知出站工具也不等于 IM 入站渠道：能推送到飞书，不代表已经实现飞书对话接入。

## 七个关键技术决策

1. **循环自己控制。** 主链路直接使用 `ChatModel.call/stream`，工具意图返回后由 ReActLoop 决定下一步，不交给另一套 Advisor 循环。
2. **执行复用统一组件。** ToolExecutor 调用注入的 ToolCallingManager，GovernedToolCallback 包装各类 ToolCallback；辅助 ChatClient 不带工具。
3. **同步结构配合虚拟线程。** Web 层采用同步调用结构；模型流式响应由 MessageAggregator 聚合完整后再处理工具意图。内部支持流式，不等于对外 SSE 端点已经交付。
4. **状态与网络调用分开。** 会话、轮次、消息和审计进入 PostgreSQL，表结构交给 Flyway；数据库事务不包住模型或工具的网络等待。
5. **记忆使用统一门面。** MemoryService 隐藏会话与长期后端差异；默认文件后端适合单机，PostgreSQL 或外部自托管后端用于不同持久化需求；情景记忆另行扩展。
6. **先定义环境策略，再提供工具。** 内置工具在 I/O 前检查白名单，非幂等操作不自动重试；远端 MCP 的权限与隔离由服务端共同承担。
7. **执行证据从基础链路开始保存。** `llm_calls` 与 `tool_invocations` 关联会话、轮次和迭代，成功失败都记录；审计查询、细粒度授权和证据保护逐步补齐。

这些决策划定了引擎与组件的分工。API 接线、配置示例和调用审计细节继续阅读 [Provider 原理与实现](/projects/agent-os/provider/)。

## 安全边界要与交付阶段一致

| 当前内核的建设要求                                 | 后续需要补齐的治理能力                   |
| -------------------------------------------------- | ---------------------------------------- |
| Profile 限定可用工具集合，内置工具执行前检查白名单 | 完整 Tool Policy、按身份授权与租户隔离   |
| 凭证从受控环境注入，日志和工具结果脱敏             | KMS/Vault 集成、轮换与细粒度凭证使用审计 |
| 工具超时、结果截断、幂等重试与调用记录             | 审计检索、报表、留存和防篡改机制         |
| 记忆与工具结果标为数据，限制写入内容               | 更系统的内容扫描与提示词注入缓解         |
| 应用层 WhitelistSandbox                            | 容器或 microVM 等更强的执行隔离          |

应用层白名单不能隔离恶意代码；允许 Python、Bash 等解释器，可能让脚本获得宿主进程的文件与网络权限。多 Agent 共用一个进程，也不代表多租户数据隔离已经成立。

## 当前状态与演进顺序

当前代码已有工程骨架、启动入口、API 规范及日志和架构检查基线。Provider、ReActLoop、MemoryService、ToolExecutor、业务表迁移和完整业务接口仍待实现；文中的能力表是目标与验收范围。

| 阶段               | 建设重点                                                        | 进入下一阶段前的证据                               |
| ------------------ | --------------------------------------------------------------- | -------------------------------------------------- |
| **运行时内核**     | 单实例承载多个 Agent 定义，贯通模型、工具、会话、记忆与基本审计 | 完成、失败、超时、工具拒绝和会话并发场景可重复验证 |
| **业务接入与治理** | 按需要补充渠道、知识库、管理接口、授权与更强隔离                | 实际业务验收、数据边界和访问控制测试               |
| **多实例高可用**   | 共享状态、工作区与定义同步、任务锁、故障收尾和容量控制          | 多实例并发一致性、节点故障恢复与负载测试           |
| **跨 Agent 协作**  | 明确委托契约、任务归属、消息可靠性和跨节点权限                  | 协作任务的可靠性与端到端追踪证据                   |

PostgreSQL 已外置，不代表应用天然无状态；默认长期记忆文件、Agent 定义和本地输出仍需处理共享与同步。数据库租约和任务锁只是高可用设计的一部分，不能单独证明集群已就绪。

## 用结果衡量平台价值

| 价值       | 可检查的结果                                                  |
| ---------- | ------------------------------------------------------------- |
| 复用底座   | 新增业务 Agent 时，主要增加定义与工具，减少重复实现会话和循环 |
| 跨系统协同 | 工具实际接通业务系统，权限、超时和错误反馈可验证              |
| 可追溯     | 一次失败能定位到会话、轮次、模型调用与工具操作                |
| 知识沉淀   | Skill 与长期记忆可维护、可检索，且不会无限扩大上下文或权限    |
| 长期维护   | 模型、工具和记忆后端替换时，核心循环与业务验收保持稳定        |

平台价值应由接入成本、完成率、失败恢复、延迟和调用成本证明，而不是由模块数量或技术栈推断。
