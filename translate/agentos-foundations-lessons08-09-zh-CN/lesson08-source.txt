--- PAGE 4 ---
 运行机制
Loop：Agent 的灵魂


 单次调用是 chatbot；在循环里反复决策、行动、观察，才是 Agent。



    Reasoning 思考        →          Acting 行动         →       Observation 观察

   基于当前状态，决定下一步                  调用一个 Tool 执行决策              拿到结果，更新进 Memory


                    ↺  未完成就带着新状态回到思考，转到任务完成或达到最大步数


  但循环不是无脑跑——它还要管这四件事：

  · 停止条件：任务完成 / 达到最大步数 / 用户中断
  · 错误恢复：工具失败时，重试、降级还是报错
  · 上下文压缩：context 越来越长时怎么裁剪历史
  · 多模型切换：不同步骤用不同模型——一个框架 80% 的复杂度都在 Loop 里

--- PAGE 5 ---
  运行机制
五组件怎么串成一个 Agent


 例子：读 README → 翻译成中文 → 写入 README.zh.md，跑一遍循环。


  入口            任务进入 Environment（文件系统），先存进 Memory（记住要干什么）


  第 1 圈         LLM 决定先读文件 → 调 read_file（Tool）→ 拿到内容（Observation）→ 回填 Memory


  第 2 圈         LLM 看到内容，决定翻译——这步它自己就能干，不调工具


  第 3 圈         LLM 调 write_file（Tool）写出中文 → 拿到「写成功」


  第 4 圈         LLM 判断任务完成 → 跳出循环


五组件一个不少：LLM 决策、Tools 是手、Memory 记忆、Loop 是发动机、Environment 是场地。

--- PAGE 6 ---
 组件深入
LLM 决策 + Tools 行动


 LLM 只下指令，干活的是框架——这个分工决定了 Agent 能做什么。


 LLM｜决策引擎                                 Tools｜行动能力

 大脑：只输出决策                                 手脚：真正改变世界

 · 理解任务、规划下一步                             · LLM 输出结构化「调用请求」，框架去执行
 · 决定调哪个 Tool、传什么参数                       · 形态：本地 / 网络 / 数据库 / MCP 远程
 · 解读结果、判断是否完成                            · Agent 的自主性边界 = Tools 的边界
 · 可单模型，也可多模型路由（强模型规划 / 快模                · MCP 让工具变成可插拔的标准件
   型合成）





管住一个 Agent，很大程度就是管住它能调哪些 Tool——这正是后面 Sandbox 要做的事。

--- PAGE 7 ---
 组件深入
Memory：Agent 会不会「成长」


 短期记忆是必需，长期记忆是高阶——有没有它，是「工具」和「助手」的分界。


 短期记忆（Context）                           长期记忆

 必需 · 一次会话内                              高阶 · 跨会话

 · 当前对话、任务进度                             · 用户偏好、项目背景、关键决策
 · 已经调用过的工具和结果                           · 实现一：结构化（MEMORY.md / SQLite）
 · 实现：直接放进 LLM 的 context window          · 实现二：向量（embedding + 相似度检索）
 · 模型窗口够大时，基本够用                          · 实现三：混合（文件 + 全文 + 向量召回）






没有长期记忆的 Agent 也是 Agent，只是每次会话都从零开始；有了它，Agent 才会「越用越懂你」。

--- PAGE 8 ---
 组件深入
Environment：能力上限与安全底线


 Agent 活在什么环境里，就能做什么——也必须在那里被约束。


 Environment 是 Agent 的「世界」              能不能在这跑，看三件事

 它能做什么的边界                               工程上的约束

 · 文件系统：能读写哪些路径                         · 能不能被工具化（有 API / SDK）
 · 网络：能访问哪些 URL                         · 权限怎么管（允许什么、禁止什么）
 · 数据库：能查哪些表                            · 副作用怎么控（破坏性操作能否回滚）
 · 用户接口：CLI / Web / IM / API            · 沙盒 Sandbox = 这一层的安全设计






Sandbox 就是给每个 Agent 一个受控的、跑坏了也不殃及别人的环境——能力上限与安全底线都在这。

--- PAGE 9 ---
   辨别
都是 Agent？又怎么分辨真假


 骨架相同，区别在 Tools 和 Environment；缺了「自主决策的循环」，就不是 Agent。


  同是 Agent，区别在哪                               这些，不是 Agent

  换 Tools、换 Environment                       缺了关键组件

  ·Claude Code / Codex：代码仓库 + 终端              ·LLM：是组件不是 Agent（CPU vs 整机）
  ·客服 Agent：IM 消息流 + 知识库 + 工单                 ·Chatbot：退掉了 Tools 和 Loop，只能聊
  ·五组件骨架完全一样                                  ·Workflow：预定义、确定性，不是自主探索
  ·区别主要在 Tools 和 Environment                  ·判据：有没有「自主决策的循环」






看到任何号称 Agent 的东西，问它的五个组件——立刻能判断它是真 Agent，还是挂羊头。

 承上启下
从单个 Agent，到 Agent OS


 企业的真问题不是「跑一个 Agent」，是「稳定地跑很多个」。


  单个 Agent                                   Agent OS

  一个智能体实例                                    支撑很多 Agent 的底座

  ·LLM + Tools + Memory + Loop + Env         · 进程管理：起、停、重启
  ·跑一个很容易                                    · 工作空间隔离 + 安全沙盒
  ·上下文集中、好控制                                 · 多模型路由 + 可观测 + 成本控制
  ·= 一个应用程序                                  · = 一个操作系统






Agent 是应用程序，Agent OS 是操作系统——L2 运行时层是 2026 最缺人的层，也是 OryxOS 要做的。
