--- PAGE 2 ---
  是什么
Agent OS 是什么


 运行和管理多个 AI Agent 的底座——装在企业自己的机器上。


  ① Agent 生命周期          注册、启动、监控、销毁多个 Agent——配置出来的，不是写代码写的


  ② 统一对外渠道              飞书 / 企业微信 / Slack / 邮件 / Web / API——所有 Agent 共用渠道层


  ③ 统一对内接入              LLM Provider、工具（MCP）、企业 IT 系统、知识库——共享接入层


  ④ 统一记忆                跨 Session 长期记忆、可复用 Skill、跨 Agent 知识沉淀


  ⑤ Tool 调用 + 沙箱        Function Calling 调 Tool，Tool 在沙箱里执行，守住安全边界


runtime 让「一个」Agent 跑起来；Agent OS 在其上再管一群：生命周期、多租户、审计。

--- PAGE 3 ---
   区别
Agent OS 和 Agent，差在哪


 一个是应用程序，一个是操作系统。


  单个 Agent                                    Agent OS

  一个智能体实例                                     支撑很多 Agent 的底座

  ·LLM + Tools + Memory + Loop + Env          ·进程管理：Agent 的起 / 停 / 重启
  ·跑一个 demo 很容易                               ·工作空间隔离 + 安全沙箱
  ·上下文集中、好控制                                  ·统一模型路由、可观测、成本控制
  ·= 一个应用程序                                   ·= 一个操作系统







企业的真问题不是「跑一个 Agent」，是「稳定地跑很多个」——这就需要 OS 这一层。

--- PAGE 6 ---
  定位
OryxOS 想做成什么样子


 一个企业能完全掌控的、分布式的 Agent 运行底座——拿来即用。


  部署起来后，业务方在上面写 skill / plugin，就有一个 agent。

  LLM 调用、message 对接、记忆压缩、运行调度——上层全不用关注，底座都实现好了，业务 Agent 直接调用。



     统一                  私有                易接入                 可观测

   共用同一套底座           数据部署全在企业手里         像装 Spring Boot 一样  标准指标、日志、管理台



把愿景收成四个词：统一、私有、易接入、可观测。

--- PAGE 7 ---
 拿来即用
业务方只写 skill，不写 agent 后端


 公共能力下沉到底座，业务方之上只管业务逻辑。


 业务方负责                                    底座负责

 只关心业务                                    全部下沉、不用感知

 · 写 Tool 实现（任何语言，走 MCP）                  · LLM 调用与多模型路由
 · 配一个 Agent：prompt、模型、Tool、渠道            · message 对接（各渠道收发）
 · 写 SKILL.md 描述任务                        · 记忆压缩与上下文管理
 · 不写任何 Agent 后端代码                        · Agent 的运行调度、多租户、审计







上一个新 Agent，不用重复造这些轮子——这就是「拿来即用」的真正含义。

--- PAGE 10 ---
    架构
五大核心能力


  Provider / Memory / Tool 供养 ReAct 引擎，Web 对外暴露。


  ① Provider             对接 LLM，屏蔽厂商差异；薄包装 Spring AI Alibaba + provider name 显式映射


  ② ReAct                核心循环引擎，约数十行、自实现，不用 Spring AI 的 Agent 抽象


  ③ Memory               三层记忆统一门面（MemoryService）；核心阶段 MEMORY.md + 两个内置 Tool


  ④ Tool                 OryxTool 抽象 + 5 个内置 Tool + Plugin 三档接入 + Sandbox 白名单


  ⑤ Web Service          REST 10 端点、虚拟线程；业务系统集成的唯一通道



一句话：Provider / Memory / Tool 三块供养 ReAct 引擎，引擎能力经 CLI / Web 两个入口对外。

--- PAGE 11 ---
  技术决策
七个关键技术决策


  这七条，定了 OryxOS 的技术骨架。


  自实现 ReAct loop                  Agent 核心完全可控，保留定制循环行为的空间


  Spring AI 只用一半                  只用 Provider 抽象 + schema 生成，禁用自动 tool 执行


  同步 + 虚拟线程                       同步阻塞模型 + JDK 21 virtual thread，单机扛高并发，不上响应式


  @Tool + OryxTool                注解生成 schema，抽象层统一内置 Tool 和 MCP Tool


  Sandbox 白名单                     Path / Pattern 白名单在应用层校验，不用已废弃的 SecurityManager


  SQLite + MEMORY.md              关系数据落 SQLite；长期记忆用 MEMORY.md + 关键词检索


  审计 day one                      tool_invocations / llm_calls 核心阶段就落库，不靠日志反解析

技术栈一句话：JDK 21 + Spring Boot 3.x + Spring AI Alibaba + 自实现 ReAct + SQLite + Picocli。                               11 /
