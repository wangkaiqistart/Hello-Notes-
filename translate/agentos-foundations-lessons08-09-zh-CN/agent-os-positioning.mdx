## 一、AgentOS 是什么

AgentOS 是运行和管理多个 Agent 的应用底座：一个目录定义一个 Agent，一个进程承载多个 Agent。它统一提供模型接入、循环执行、会话、记忆、工具、入口和调用审计，让业务 Agent 复用公共运行能力。

AgentOS 面向需要私有部署、复用 Java 服务并追踪执行过程的团队。它不是一个聊天页面，也不是只提供模型调用的 SDK；平台目标是把 Agent 的公共运行能力沉淀成可以替换、可以验收的基础设施。

AgentOS 需要统一处理的内容包括：

1. Agent 定义、Profile 派生和生命周期入口。
2. CLI、REST 及后续消息渠道的接入。
3. Provider、Tool、MCP 和业务系统的对内连接。
4. Session、Memory、工作区和调用记录的管理。
5. ReAct 循环、工具执行、超时、权限和审计。

Runtime 让一个 Agent 跑起来；AgentOS 在 Runtime 之上管理一组 Agent 的共享能力和约束。两者是层次关系，而不是两个必须独立部署的进程。

## 二、AgentOS 和 Agent，差在哪里

| 单个 Agent             | AgentOS                           |
| ---------------------- | --------------------------------- |
| 一个智能体应用实例     | 承载多个智能体的运行底座          |
| 关注一次任务能否完成   | 关注多个 Agent 能否持续稳定运行   |
| 一组上下文和工具       | 多 Agent 的会话、工作区和工具边界 |
| 手动指定一个模型       | Provider 映射、模型路由和调用审计 |
| 出错后查看单个日志     | 统一状态、失败记录和故障定位      |
| 进程生命周期由应用负责 | 统一管理定义、触发、轮次和收尾    |

AgentOS 是用户态应用，不接管操作系统内核调度，也不要求每个 Agent 对应一个操作系统进程。Agent 的注册与注销、轮次的开始与结束、宿主应用的启动与关闭，是三种不同的生命周期。

与相邻概念的边界也要清楚：模型框架提供基础 API，Workflow 平台编排确定步骤，业务 Agent 负责具体目标；AgentOS 负责把这些能力组织成可持续运行的底座。

## 三、企业为什么需要私有可控的底座

企业关注的不是“Agent OS”这个名称，而是数据、执行和责任能否受到控制。需要重点回答四个问题：

| 企业约束         | 需要落成的工程能力                                                |
| ---------------- | ----------------------------------------------------------------- |
| **数据不出企业** | 模型、Embedding、MCP、工具下游、记忆和日志的出口可控              |
| **完全可追溯**   | 能关联谁、何时、通过哪个 Agent 调用了什么模型和工具，以及结果如何 |
| **纳入 IT 治理** | 认证、权限、密钥、漏洞、监控、发布和应急流程接入既有体系          |
| **技术栈对齐**   | 能复用 Java 服务、数据库、运维和合规设施                          |

私有部署不自动等于数据不出域：只要使用外部模型或远程 MCP，就必须明确发送的数据和端点。写入 `llm_calls`、`tool_invocations` 是审计基础，也不能单独替代访问控制、留存策略和防篡改机制。

## 四、AgentOS 的平台定位

AgentOS 的定位可以收敛为四个词：**统一、私有、易接入、可观测。** 每个词都对应可检查的行为：

| 定位       | 要证明什么                                             | 不能直接推断什么                              |
| ---------- | ------------------------------------------------------ | --------------------------------------------- |
| **统一**   | CLI、REST 和定时入口复用 AgentService 和同一条运行链路 | 所有 Agent 自动拥有相同权限或可以共享全部数据 |
| **私有**   | 部署、存储、网络出口和凭证由企业控制                   | 应用在内网，就不会向外部模型或 MCP 发送数据   |
| **易接入** | 新业务优先复用 Agent 定义、Skill 和已有 Tool           | 只写一段提示词就能跳过接口、权限和业务验收    |
| **可观测** | 轮次、模型与工具记录可以关联，失败原因可追溯           | 有控制台日志，就已经具备完整审计或成本账单    |

业务 Agent 保留目标、规则、领域知识和权限边界；AgentOS 负责公共运行能力。平台价值不在于替业务方决定所有内容，而在于减少每个 Agent 重复建设会话、循环、工具治理和审计的成本。

### 与相邻开源 Agent 项目的位置

这里仅比较工程取向，不把未经当前项目验证的市场数据或成熟度当作事实：

| 项目         | 主要取向                           | 与 AgentOS 的差异                                       |
| ------------ | ---------------------------------- | ------------------------------------------------------- |
| OpenClaw     | Node.js 生态、渠道和社区扩展       | AgentOS 更强调 Java 服务复用、私有部署和企业运行边界    |
| Hermes Agent | Python 生态、记忆和 Agent 能力探索 | AgentOS 以 Spring Boot、PostgreSQL 和显式治理契约为基础 |
| AgentOS      | Java 运行底座、可审计和可扩展      | 当前仍处于工程骨架阶段，治理能力按路线逐步实现          |

对比的意义是明确边界，而不是宣称某个项目天然安全或已经满足企业合规。

## 五、业务方如何定义一个 Agent

Agent 定义采用目录结构：frontmatter 提供运行配置，正文描述业务任务，Skill、脚本和参考资料按需放在目录中。

```text
.AgentOS/
  agents/
    ops-agent/
      AGENT.md          # frontmatter 派生 Profile，正文是任务指令
      skills/           # 指向公共 Skill 的相对软链接
      scripts/          # 可选脚本
      REFERENCE.md      # 可选参考
  skills/               # 公共 Skill
  memory/MEMORY.md      # 默认长期记忆文件
  mcp_servers.yaml      # MCP 服务配置
```

全局连接放在 `application.yaml`；Agent 显式选择 provider、聊天模型和工具。AgentLoader 负责校验并派生 Profile，ContextLoader 负责加载任务指令、Bootstrap 和可见 Skill 的元数据。

| 对象           | 业务方提供什么                   | 底座负责什么                                 |
| -------------- | -------------------------------- | -------------------------------------------- |
| **Agent 定义** | 目标、约束、模型、工具和触发规则 | 校验、Profile 索引、上下文构建和执行         |
| **Skill**      | 可复用的方法、脚本和参考资料     | 发现绑定关系，先展示元数据，再按需读取正文   |
| **Tool**       | 可调用的业务能力及参数契约       | 注册、权限过滤、执行、超时、结果处理和审计   |
| **MCP 服务**   | 通过协议暴露的远程工具           | 连接、发现和回调适配；服务端仍负责权限与隔离 |

“业务方只写 Skill”只能作为接入目标，不能理解为无需工具实现、接口开发、权限配置和验收。Skill 不是 Tool，MCP 也不会自动授予企业系统访问权限。

## 六、为什么选择 Java

Java 的理由来自企业运行环境和长期维护要求：

- Spring Boot 已经进入大量企业服务的开发、部署、监控和审计链路。
- JVM 生态拥有成熟的数据库、配置、限流、追踪和服务集成组件。
- AgentOS 可以直接调用现有 Java 服务和内部 API，减少跨栈胶水。
- JDK 21 的虚拟线程适合保留同步调用结构，但不增加数据库连接数、模型配额或下游容量，仍需并发限制和容量测试。

技术栈当前锁定为 JDK 21、Spring Boot 4.1.2、Spring AI 2.0.2、Spring MVC、PostgreSQL/pgvector、JPA、Flyway、Picocli 和 MCP Client。Java 本身不自动带来安全或分布式能力，权限、超时、审计、故障恢复和容量仍需验证。

## 七、整体架构：四层与九个模块

CLI、REST 和定时触发都汇入 AgentService；引擎协调 Provider、Memory 和 Tool，支撑层加载定义、保存状态并约束 I/O。四层是职责视图，不等于四个 Maven 模块。

| 层               | 主要职责                                   | 典型组成                                                            |
| ---------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| **接入与触发层** | 接收消息或定时事件，返回结果和状态         | CliChannel、REST、AgentScheduler                                    |
| **运行引擎层**   | 组织上下文、模型调用、工具执行和终止判断   | AgentService、ReActLoop、PromptBuilder、ToolExecutor                |
| **能力层**       | 提供可替换的模型、记忆和工具能力           | ProviderService、MemoryService、ToolRegistry、MCP Client            |
| **支撑与存储层** | 加载配置、保存状态、约束 I/O、记录调用过程 | AgentLoader、ContextLoader、PostgreSQL、Flyway、Sandbox、日志与审计 |

项目根 POM 当前包含九个核心模块：

| 模块                  | 职责                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------- |
| `AgentOS-core`        | Profile、TurnContext 等契约，AgentService、ReActLoop、PromptBuilder、ToolExecutor、加载与调度编排 |
| `AgentOS-provider`    | 具名 ChatModel 映射、模型请求、重试、元数据和独立 EmbeddingModel                                  |
| `AgentOS-memory`      | MemoryService、SessionManager、LongTermMemoryStore 和记忆工具                                     |
| `AgentOS-tool`        | 内置工具、MCP Client、ToolRegistry、GovernedToolCallback 和 Sandbox                               |
| `AgentOS-storage`     | PostgreSQL 数据源、会话与审计持久化、Flyway 迁移和任务锁存储                                      |
| `AgentOS-web`         | REST 接入、响应规范、异常映射和接口文档                                                           |
| `AgentOS-channel-cli` | 交互式对话渠道                                                                                    |
| `AgentOS-cli`         | Picocli 命令入口、配置和命令分发                                                                  |
| `AgentOS-boot`        | 应用启动、依赖聚合和组件装配                                                                      |

模块名称表达当前工程组织；业务类、迁移脚本和完整运行链路仍按 user story 逐步实现。

## 八、五大核心能力

| 能力            | 核心契约                                                                   |
| --------------- | -------------------------------------------------------------------------- |
| **Provider**    | 按 provider 名称显式选择连接，使用完整请求选项，返回原始响应，记录每次尝试 |
| **ReAct**       | 自行控制迭代、工具反馈、终止条件和轮次状态                                 |
| **Memory**      | 区分完整会话记录、本轮上下文和长期事实，控制加载预算                       |
| **Tool**        | 统一回调与执行入口，处理权限、I/O 超时、幂等性、脱敏和审计                 |
| **Web Service** | 向业务系统提供会话与 Agent 调用接口，明确同步等待和后台轮次关系            |

Provider、Memory 和 Tool 供养 ReAct 引擎；CLI、REST 和定时任务复用同一条 AgentService 链路。通知出站工具不等于 IM 入站渠道，能推送消息不代表已经实现对话接入。

## 九、七个关键技术决策

1. **循环自己控制。** 主链路直接使用 `ChatModel.call/stream`，工具意图返回后由 ReActLoop 决定下一步，不交给另一套 Advisor 循环。
2. **执行复用统一组件。** ToolExecutor 调用注入的 ToolCallingManager，GovernedToolCallback 包装各类 ToolCallback；辅助 ChatClient 不带工具。
3. **同步结构配合虚拟线程。** Web 层采用同步调用结构；模型流式响应由 MessageAggregator 聚合完整后再处理工具意图。内部支持流式，不等于对外 SSE 端点已经交付。
4. **状态与网络调用分开。** 会话、轮次、消息和审计进入 PostgreSQL，表结构交给 Flyway；数据库事务不包住模型或工具的网络等待。
5. **记忆使用统一门面。** MemoryService 隐藏会话与长期后端差异；默认文件适合单机，PostgreSQL 或自托管后端用于不同持久化需求。
6. **先定义环境策略，再提供工具。** 内置工具在 I/O 前检查白名单，非幂等操作不自动重试；远程 MCP 的权限和隔离由服务端共同承担。
7. **执行证据从基础链路开始保存。** `llm_calls` 与 `tool_invocations` 关联会话、轮次和迭代，成功失败都记录；查询、细粒度授权和证据保护逐步补齐。

## 十、安全：能力和交付阶段一致

| 当前内核的建设要求                                 | 后续需要补齐的治理能力                 |
| -------------------------------------------------- | -------------------------------------- |
| Profile 限定可用工具集合，内置工具执行前检查白名单 | 完整 Tool Policy、按身份授权和租户隔离 |
| 凭证从受控环境注入，日志和工具结果脱敏             | KMS/Vault 集成、轮换和细粒度凭证审计   |
| 工具超时、结果截断、幂等重试和调用记录             | 审计检索、报表、留存和防篡改机制       |
| 记忆与工具结果标为数据，限制写入内容               | 更系统的内容扫描和提示词注入缓解       |
| 应用层 WhitelistSandbox                            | 容器或 microVM 等更强的执行隔离        |

应用层白名单是劝阻级防线，不能隔离恶意代码；允许 Python、Bash 等解释器可能让脚本获得宿主进程的文件与网络权限。多 Agent 共用一个进程，也不代表多租户数据隔离已经成立。

## 十一、从单机到分布式

演进要先解决状态、工具和治理边界，再外置状态和拆分服务：

| 阶段                        | 重点                                                                           | 进入下一阶段前的证据                           |
| --------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| **当前：单机私有部署**      | 一个实例承载多个 Agent 定义，贯通 Provider、Loop、Memory、Tool、入口和基本审计 | 完成、失败、超时、工具拒绝和会话并发可重复验证 |
| **中期：多实例底座**        | 共享状态、工作区和定义同步，任务锁、故障收尾和容量控制                         | 多实例并发一致性、节点故障恢复和负载测试       |
| **远期：分布式 Agent 协作** | 明确委托、消息可靠性、跨节点权限和全链路追踪                                   | 协作任务可靠性与端到端追踪证据                 |

PostgreSQL 已外置，不代表应用天然无状态；默认长期记忆文件、Agent 定义和本地输出仍需要共享与同步策略。数据库租约和任务锁只是高可用设计的一部分。

## 十二、价值落点

| 价值       | 可检查的结果                                                |
| ---------- | ----------------------------------------------------------- |
| 复用底座   | 新增业务 Agent 时主要增加定义和工具，减少重复实现会话与循环 |
| 跨系统协同 | 工具实际接通业务系统，权限、超时和错误反馈可验证            |
| 可追溯     | 一次失败能定位到会话、轮次、模型调用和工具操作              |
| 知识沉淀   | Skill 与长期记忆可维护、可检索，不无限扩大上下文或权限      |
| 长期维护   | 模型、工具和记忆后端替换时，核心循环和业务验收保持稳定      |

平台价值应由接入成本、完成率、失败恢复、延迟和调用成本证明，而不是由模块数量或技术栈推断。

## 十三、当前状态与阅读路径

当前项目已有 Maven 骨架、启动入口、API 规范、日志和架构检查基线。Provider、ReActLoop、MemoryService、ToolExecutor、业务表迁移和完整业务接口仍待实现；本文中的能力表是目标与验收范围。
