## 三个典型反面案例

| 案例 | 别名 | 症状 | 根因 | 对应原则 |
|------|------|------|------|---------|
| ai-dev-assistant | 万能瑞士军刀 | 任何请求都触发、执行时不断分支判断 | 一个 Skill 承担十几个职责 | SRP |
| code-bomb-deployer | 厨房水槽 | Agent 分不清指令和参考资料 | 代码/配置/文档全混在 SKILL.md | SoC |
| encyclopedia-translator | 文档搬运工 | Agent 迷失在 2847 行文档中 | 未区分背景知识和执行要点 | 信息精炼 |

**本质误区**：把 Skill 当"知识库"而非"执行指令"。好 Skill 像作战指令（清晰、简洁、可执行），不是参考手册。

## 三大设计原则

### 1. 单一职责原则（SRP）

> 一个 Skill 只解决一个问题，只有一个调用理由。

**验证方法：**
- **一句话测试** — 描述需要"和/或/以及"连接？不单一
- **变化原因测试** — 可能导致修改的原因 > 1 个？不单一
- **调用场景测试** — 使用场景之间无强关联？不单一

**拆分方法**：按用户要解决的问题域分解，检查问题独立性，定义清晰的输入输出。

<Aside type="caution">
宁可多几个小 Skill，也不要一个大而全的 Skill。
</Aside>

### 2. 关注点分离（SoC）

| 信息类型 | 存放位置 | 变化频率 | 读取者 |
|---------|---------|---------|--------|
| 执行指令 | SKILL.md | 低 | Agent |
| 代码实现 | scripts/*.py | 中 | 解释器 |
| 配置参数 | assets/templates/ 或环境变量 | 高 | 脚本运行时 |
| 领域知识 | references/ | 低 | Agent（按需引用） |

**标准目录结构：**

<FileTree>
- my-skill/
  - SKILL.md （路由层，100-500行）
  - scripts/ （可执行脚本，按功能拆分）
    - process_data.py
    - validate.py
  - references/
    - core/ （必读）
    - advanced/ （可选）
  - assets/ （输出模板和示例）
  - agents/ （子 Agent，可选）
  - tests/ （可选）
</FileTree>

### 3. 信息精炼原则

```
SKILL.md = 执行步骤 + 关键参数 + 异常处理 + 文档引用
```

**三步过滤法：**

<Steps>
1. **识别执行路径** — 只留"完成任务的步骤"，砍背景和原理
2. **提取关键参数** — 只留必需参数，砍可选和默认值
3. **标注异常情况** — 只留会导致失败的情况，砍边缘 case
</Steps>

## Skill 三层架构

```
路由层 (frontmatter)    → 要不要激活       （3-5 行）
控制层 (SKILL.md 正文)  → 怎么做决策       （60-100 行）
执行层 (scripts/等)     → 具体怎么做       （不限）
```

控制层核心六部分：Goal、Workflow、Decision Tree、Constraints、Validation、Resources。

SKILL.md 是路由层，不是教科书。首要任务是帮 Agent 快速判断下一步该做什么。

## 七种设计范式

### 频率与选型

| 范式 | 频率 | 一句话 | 典型场景 |
|------|------|--------|---------|
| **Operator** | 40% | 输入确定 → 固定工具链 → 输出稳定 | 格式转换、文档处理、代码生成 |
| **Scout** | 25% | 先侦察再行动，证据驱动 | Bug 定位、代码分析、系统诊断 |
| **Partner** | 20% | AI 组织过程，用户做关键决策 | 需求梳理、方案设计 |
| **Navigator** | 10% | 输入 → 定位正确资源/入口 | 知识检索、任务分发 |
| Philosopher | 少 | 基于原则输出判断 | 代码评审、架构评估 |
| Architect | 少 | 从需求到系统方案 | 技术选型、架构规划 |
| Orchestrator | 少 | 编排多工具协作 | 跨系统集成 |

### Scout 四阶段循环

探测（Probe）→ 分析（Analyze）→ 验证（Verify）→ 报告（Report）

<Aside type="tip">
这四阶段不是线性的，会随新证据不断回跳迭代。
</Aside>

### 选型决策树

```
环境已知且步骤固定？ → Operator
需要多轮探索？     → Scout
需要用户确认？     → Partner
需要路由/查找？    → Navigator
需要原则判断？     → Philosopher
需要系统设计？     → Architect
需要多工具协调？   → Orchestrator
```

## 五维度质量评估

<CardGrid>
  <Card title="触发质量" icon="seti:config">
    该触发时触发，不该触发时不触发
  </Card>
  <Card title="路由质量" icon="right-arrow">
    流程路径清晰，分支明确，Agent 能快速判断下一步
  </Card>
  <Card title="上下文效率" icon="compress">
    SKILL.md 精简，Agent 能快速提取要点
  </Card>
  <Card title="复用与确定性" icon="approve-check-circle">
    同输入执行三次，输出结构稳定一致
  </Card>
</CardGrid>

**维度5：验证强度** — 有明确的成功标准、失败检查点和结果验证机制。

每维度 1-5 分，满分 25 分。**最低分的维度 = 最该优先改的地方。**

## 评估驱动迭代

Skill 不会自动变好。正确路径：

```
v1 → 评估 → 诊断 → 排优先级 → 定向改进 → 再验证 → 循环
```

### 三层组合

| 层 | 回答 | 做什么 |
|----|------|--------|
| 遥测采集 | 发生了什么 | 记录触发、误触发、输出质量、耗时 |
| 定期复盘 | 为什么 | 从数据中提取规律 |
| 实际升级 | 怎么改 | 人工判断改哪里 |

<Aside type="caution">
跳过遥测和复盘直接改 = 凭感觉修补，低效且容易走偏。
</Aside>

## 附录：Skills 在系统中的流转

```
文件系统扫描 SKILL.md → 生成快照注入 System Prompt → Agent 路由到 Skill → 执行 Workflow → 调用 scripts/ → 返回输出
```

设计阶段的每个决策，最终都会影响系统的路由质量和执行稳定性。
