> **重点**：Loop Engineering 不是让 Agent 多跑几轮，而是把目标、触发、上下文、工具、状态、验证、预算和退出条件设计成闭环。

## Agent Loop 与 Loop Engineering

Agent Loop 是一次任务内部的 `Reason → Act → Observe`。Loop Engineering 把它放到更大的系统里：自动发现任务、调度 Agent、记录状态、独立验证，失败时重试或升级人工。

一次运行要显式区分成功、可重试失败和需要人工处理的失败；只有预算允许且问题可修正时才继续循环。

## 设计清单

- 目标：最终要达成什么；
- 触发：定时、事件还是目标驱动；
- 工作空间：在哪里安全操作；
- 委托：谁执行、谁验证、谁调度；
- 状态：进度和中间结果放在哪里；
- 验证：用测试、状态、金额或独立 Checker 证明什么；
- 预算：最大轮数、时间、Token 和工具调用次数；
- 退出：成功、失败、超预算和人工接管如何结束。

## 稳定性原则

- 重试必须有上限和退避，不能交给模型自由决定。
- 不可逆操作前要有权限边界和独立复核。
- 运行状态必须持久化，否则进程重启后无法解释进度。
- 关键路径要有日志、成本、成功率和异常指标。

## 开发任务怎样进入循环

**要点**：先准备能判定结果的验收，再让 Agent 开始实现。目标只有“优化代码”“提高质量”时，循环无法可靠判断自己是否完成。

以“修复日期解析器错误接受非法日期”为例，一张任务卡片可以这样写：

```yaml title="任务卡片示例"
id: date-parser-01
goal: 拒绝 2026-02-30 等不存在的日期
scope: 日期解析函数及对应单元测试
non_goals: 不调整日期格式，不引入新依赖
acceptance:
  - 合法日期及闰年日期仍能解析
  - 非法日期返回既定错误，不自动滚动到下个月
verification:
  - 先运行能复现错误的回归测试，确认失败原因
  - 修复后运行日期解析测试和相关调用方回归
boundaries:
  - 不删除、跳过或放松既有验收断言
  - 需求或错误语义不明确时交给人处理
budget: 最多 3 轮修正；仍未通过则交接证据
```

这里的轮数是示例预算，实际值要按失败代价和反馈成本确定。任务允许编写新的回归测试，但不能为了变绿而擅自改变已经确认的验收含义。

执行时按以下顺序推进：

1. **确认基线**：阅读任务、规则和依赖，在隔离分支或工作目录中确认已有检查状态。
2. **建立反馈**：新增或选定能复现问题的测试；TDD 场景下实际运行，确认测试因目标行为缺失而失败。
3. **最小实现**：只修改当前任务需要的行为，避免顺手扩大重构范围。
4. **读取结果**：运行快速检查，记录命令、退出状态、失败用例和关键输出。
5. **有界修正**：根据失败提出可验证的假设；有新证据且预算足够才继续。
6. **交接验收**：本地检查通过后，交给独立审查和外部检查；通过当前任务的门禁，再推进依赖它的任务。

下图把局部修正与最终验收分开：本地变绿只代表可以提交复核，外部验收仍可能发现问题并要求修正。

### 批量任务的状态与交接

按依赖顺序执行任务；前置任务失败时，停止依赖它的后续任务。互不依赖的任务只有在接口明确、写入范围分离时才适合并行。

每个任务可以使用新的 Agent 上下文，减少前一个任务的尝试过程污染后续判断。新的上下文仍要读取必要的规则、规格和状态，不能丢掉约束。状态放在文件或调度系统里，至少记录任务编号、基线版本、进度、检查结果、阻塞点和下一步。

```yaml title="外置任务状态示例"
task: date-parser-01
status: awaiting_review
attempts: 2
checks:
  parser_regression: passed
  caller_regression: passed
external_acceptance: pending
next: 独立审查差异与回归用例
```

恢复任务前，应核对代码版本和测试记录是否仍然对应当前状态。重启后直接重放上次不确定的操作，可能制造重复变更或外部副作用。

## 保护验收标准

**重点**：实现者需要测试反馈，但不能拥有随意改写评分标准的权力。删除失败用例、降低断言强度、跳过困难场景，都可能让循环“成功”而行为仍然错误。

| 角色或机制 | 可以做什么                           | 需要守住的边界                       |
| ---------- | ------------------------------------ | ------------------------------------ |
| 实现 Agent | 修改实现、新增回归用例、运行本地检查 | 不擅自弱化既定验收、不把失败标成通过 |
| 独立审查   | 对照规格、差异和运行证据复核         | 不只重复实现者的解释，要检查实际产物 |
| 外部 CI    | 在明确版本上执行验收和回归           | 验收脚本与权限受保护，修改需单独审查 |
| 人         | 裁定需求与验收变更、判断剩余风险     | 区分实现错误与测试错误，记录修订理由 |

“禁止改验收”针对绕过目标的行为。发现测试本身写错时，应先说明冲突、评审新的预期，再同步修改规格和测试。把所有测试永远冻结，同样会妨碍正常维护。

另开一个 Agent 不能自动保证验证独立；如果它只能看到实现者的总结，或者两者共享可随意修改的验收脚本，保护仍然很弱。更强的边界来自独立的检查依据、受保护的配置和执行权限。

## 快速反馈与外部验收

循环每轮需要及时反馈，昂贵或有破坏性的检查则需要受控环境。测试分组要按真实耗时、副作用和风险决定，不能只凭“单元”“集成”的名称判断。

| 放置位置           | 适合的检查                                   | 主要目的                             |
| ------------------ | -------------------------------------------- | ------------------------------------ |
| 每轮本地执行       | 目标回归、快速单元或集成测试、类型检查、Lint | 快速发现当前修改的问题，指导下一轮   |
| 任务或模块交接     | 相关模块回归、构建、规格符合性和代码质量审查 | 检查局部修复是否影响相邻行为         |
| 外部 CI 或独立环境 | 较慢的端到端、故障注入、性能与安全检查       | 验证完整路径、复杂时序和环境相关风险 |

用关键失败模式设计断言。例如“非法日期必须拒绝”比单独要求覆盖率达到某个百分比，更能说明当前任务验收什么。覆盖率可帮助发现未执行代码，但不能证明断言有效或业务正确。

## 三层反馈与人工检查点

开发循环应嵌在更大的反馈里：内层用测试修正代码，中层由人检查规格、设计和变更，外层通过实际使用、运行指标和用户反馈判断问题是否解决。

| 反馈层     | 回答的问题                           | 不能替代什么                 |
| ---------- | ------------------------------------ | ---------------------------- |
| 代码与测试 | 当前实现是否符合已编码的检查？       | 不能替代对验收完整性的判断   |
| 人工审查   | 是否做对需求，设计是否可维护？       | 不能替代真实环境中的运行证据 |
| 实际使用   | 是否解决问题，收益与风险是否可接受？ | 不能因为短期无投诉就省略回归 |

检查点可以按任务或模块设置。高代价、难验证、不可逆的环节要收紧自主范围；规则明确、反馈可靠、影响可恢复的环节才适合扩大自动化。

`/loop` 可以是某个工具或本地 Skill 提供的入口，不是所有编程助手都内置的通用命令。使用前要检查它读取什么任务、能改什么、如何验证和停止。
