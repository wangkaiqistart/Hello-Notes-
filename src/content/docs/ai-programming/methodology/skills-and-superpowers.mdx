> **重点**：Skill 不是更长的 Prompt，而是带触发条件、执行步骤、边界和验证方式的可复用能力模块。

## Skill 的两类价值

- **能力提升**：让 Agent 学会调用工具、执行测试、整理资料或完成某类流程。
- **偏好编码**：把团队的架构风格、审查标准和禁止事项固定下来。

一个合格的 Skill 至少说明：什么时候触发、需要什么输入、按哪些步骤执行、失败怎么处理、什么证据算完成。

## 渐进式加载

加载分成三个阶段：先判断是否适用，再读取执行流程，最后按需打开参考资料和脚本。

[![Skill 渐进式加载：元数据负责发现，正文提供流程，参考资料与脚本按需打开](/images/ai-programming/notes/skill-loading.svg)](/images/ai-programming/notes/skill-loading.svg)

Skill 越多越要重视描述的准确性、命名冲突和验证成本。

## Skill、MCP、子 Agent 与插件

这些机制可以配合使用，但解决的问题不同：

| 机制       | 回答的问题                             | 示例                                        |
| ---------- | -------------------------------------- | ------------------------------------------- |
| Skill      | 这类任务按什么经验和步骤完成？         | API 审查清单与验证流程                      |
| MCP / Tool | Agent 通过什么接口取得数据或执行动作？ | 读取接口定义、运行检查工具                  |
| Subagent   | 谁在怎样的上下文和职责下处理子任务？   | 独立探索代码或审查实现                      |
| Plugin     | 如何分发一组相关能力与集成？           | 打包 Skills、工具和配置，具体内容由平台决定 |
| 命令入口   | 用户怎样显式启动一个流程？             | 调用一个审查 Skill                          |

Skill 提供做法，工具提供动作，子 Agent 承载执行与上下文；插件负责组合和分发。安装某个 Skill 并不自动授予它访问数据库、凭据或外部系统的权限。

## 写一个能触发、能验收的 Skill

结构与字段的完整示例见 [Skill 基础](/agent/skills/basics/#skill-的内部三层结构)。正文保留高频流程，长篇约定放到 `references/`，确定性操作放到 `scripts/`，完整输入输出放到 `examples/`，并写明在什么步骤读取或运行。

下面以 Spring MVC 接口审查为例。返回体、异常处理与校验规则应以当前代码仓约定为准，不能把某种团队风格当成所有 Spring 应用的统一标准。

```markdown title="spring-api-review/SKILL.md 示例"
---
name: spring-api-review
description: 审查 Spring MVC 接口的参数校验、错误语义和兼容性。用于审查 Controller、接口变更或参数校验；不用于生成新接口、审查前端页面或执行生产修复。
---

# Spring MVC 接口审查

## 输入

需要审查的差异或接口路径、验收要求、仓内接口约定。

## 步骤

1. 读取项目指南和接口约定，确认 JDK、Spring 与校验 API 版本。
2. 从 Controller 追踪请求 DTO、Service 和异常处理，区分接收、处理与返回。
3. 检查必填、格式、边界与嵌套对象校验，核对错误码和返回体契约。
4. 检查权限、兼容性与副作用；按项目命令运行必要的针对性验证。
5. 按严重程度报告问题，提供文件位置、触发条件、影响和验证结果。

## 边界与验收

- 默认只审查，不自动修改、部署或执行数据修复。
- 不假定必须使用某个统一返回体类或某种校验注解。
- 结论必须有代码或运行证据；未验证的推断单独说明。
- 没有发现问题时，也说明检查范围和剩余验证缺口。
```

### 用正反例检查触发边界

description 需要同时说明任务、场景和排除条件。只写“处理代码”会与大量 Skill 重叠；堆很多技术名词也无法替代清楚的职责。

| 请求                                 | 期望行为          | 验证重点                         |
| ------------------------------------ | ----------------- | -------------------------------- |
| “审查这个订单 Controller 的参数校验” | 使用该 Skill      | 是否追踪 DTO、调用链和异常处理   |
| “新增一个订单查询接口”               | 不由该 Skill 主导 | 是否避免把审查流程误用成实现流程 |
| “看看 React 表单校验”                | 不使用该 Skill    | 是否识别技术与职责边界           |
| “直接改生产数据修复这个错误”         | 不执行修复        | 是否遵守审查权限和副作用边界     |

验证分两层：先看是否在正确的请求上触发，再看触发后是否执行正确。除了顺利案例，还要放入输入不全、命令失败、约定冲突和权限不足的情况。已有多个相关 Skill 时一起试跑，观察重复调用和职责冲突。

## 作用域、版本与维护

| 作用域   | 适合放什么                           | 维护重点                                 |
| -------- | ------------------------------------ | ---------------------------------------- |
| 个人     | 通用习惯、个人工具操作、跨仓任务方法 | 避免把个人偏好误当成项目规则             |
| 项目     | 当前仓库的约定、命令、目录和业务检查 | 随代码一起审查和更新，优先保证可复现     |
| 团队共享 | 多个仓库共同使用的稳定流程           | 明确维护者、发布版本、兼容范围和升级方式 |

作用域的实际目录、发现顺序和同名覆盖规则取决于助手实现。项目级能力应保留明确名称与边界，不能只依赖“覆盖全局同名文件”来保证正确加载。

一次可维护的变更至少留下：修改原因、兼容的工具与运行环境、依赖脚本、验证案例和结果。版本号可以记录在仓库标签或变更记录中，不要假定所有加载器都会理解自定义版本字段。

维护时重点做四件事：

1. **审查安装内容**：读实际指令、脚本、网络访问和写入范围，不凭 Star 或名称判断可靠性。
2. **合并重复职责**：同一类审查尽量保留一个主流程，领域细则按需引用。
3. **控制更新**：共享能力固定可复现版本，升级后重新验证触发和执行行为。
4. **淘汰失效规则**：为弃用能力注明替代入口，清理旧副本，避免新旧规则同时命中。

## Superpowers 的定位

Superpowers 是一套 agentic Skills 框架和软件工程方法论。它把头脑风暴、写规格、写计划、TDD、Subagent、Review、系统化调试等纪律嵌进 Agent 工作流。

它和 SDD 工具的关系可以这样记：

| 能力                | 主要职责                          |
| ------------------- | --------------------------------- |
| Spec-Kit / OpenSpec | 把需求变成规格和变更流程          |
| Superpowers         | 让 Agent 在各种任务中遵守工程纪律 |
| 项目级 Skill        | 编码团队自己的领域知识和约束      |

## Superpowers 的执行主线

**重点**：把需求理解、任务拆分、实现、审查和收尾连接起来，并让每个阶段留下可检查的产物。

1. **澄清与设计**：理解目标、非目标、边界与候选方案，形成足以实施的设计。
2. **准备工作空间**：按需要建立隔离分支或 worktree，确认安装与测试基线。
3. **拆分计划**：每个任务写清输入、依赖、文件范围、实现目标和验证步骤。
4. **逐项实现**：选择当前会话执行或子 Agent 执行，对适合的行为变更使用 TDD。
5. **审查与修正**：核对规格符合性、代码质量及相关回归，再检查整体差异。
6. **收尾交接**：运行最终验证，说明完成项和剩余风险，选择提交评审、保留分支等后续动作。

这条主线中，TDD 穿插在具体任务里，审查可以逐任务执行并在末尾检查整体。小范围明确修改可以缩短前期讨论；复杂变更则需要更充分的设计和计划。

### 两个审查维度

| 审查维度   | 必须核对的内容                               | 典型问题                                     |
| ---------- | -------------------------------------------- | -------------------------------------------- |
| 规格符合性 | 要求是否完整实现，是否越界，失败行为是否一致 | 少做异常路径、多做未要求功能、改变既有语义   |
| 代码质量   | 结构、复杂度、维护性、测试和潜在缺陷         | 需求满足但并发不安全、重复实现、测试断言无效 |

先检查有没有做对要求，再判断实现是否可靠。两阶段可以由独立角色完成，也可能在同一次任务审查中检查两个维度，具体编排随版本变化。无论怎样组织，都需要实际查看差异、规格和测试记录。

### 真正运行红、绿、重构

TDD 的“红”不是写出一个看上去会失败的测试，而是运行它，确认它因缺失目标行为而失败。环境缺包、导入错误或语法错误不等于已经复现了业务缺陷。

随后写最小实现让测试通过，再在测试保护下重构。已有测试全部绿色时，应检查它是否真的覆盖当前变更；涉及文案、格式或低影响配置时，则选择合适的检查，不必机械套用同样的测试流程。

### 根因分析与完成证据

系统化调试应先复现、收集调用链与环境证据，再提出假设、做最小实验、修复并回归。连续修改多个无关点，即使最后变绿，也很难解释真正原因。

宣称完成前，应运行与当前代码版本相符的验证，报告命令、结果和范围。旧版本的绿色记录、实现者自评、任务清单勾选，都不能代替当前证据。

### 上下文与工作空间分别隔离

新的子 Agent 上下文可以减少任务间的历史干扰；worktree 则隔离文件与分支。二者并不一一对应：多个任务可以在一个受控 worktree 中串行执行，只有独立并行且需要分离写入时，才考虑分别建立工作空间。

是否委派还要权衡启动、上下文传递和审查成本。改错别字、小段明确修改、强依赖任务，不一定需要多个 Agent。工作空间也不能代替工具权限和真正的运行沙箱。

### 与规格工具配合

Spec-Kit 或 OpenSpec 可以负责规格、方案和任务，Superpowers 可以承担实现纪律、TDD、调试与审查。组合时明确哪份规格和任务清单是共同依据，避免两套 Skill 同时生成互相矛盾的计划。

触发条件、Skill 名称和审查编排以安装版本为准，可对照 [Superpowers 官方说明](https://github.com/obra/superpowers)。自动触发不代表每个任务都需要完整流程，也不代表合并、发布或外部操作已获得授权。

## Skill 的沉淀流程

1. 从真实重复任务中识别模式。
2. 写触发条件、输入、步骤、失败处理和验收。
3. 用一个真实任务试跑，观察 Agent 是否按流程执行。
4. 把失败案例补进 Skill，而不是无止境增加说明。
5. 删除过时或无法验证的 Skill。
