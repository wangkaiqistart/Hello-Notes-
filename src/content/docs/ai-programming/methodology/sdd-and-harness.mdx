> **重点**：SDD 定义“做什么、做到什么程度”，Harness 约束“在什么边界内、按什么流程完成”。规格工具帮助维护这些约定。

## SDD 定义目标

Spec-Driven Development 把目标、范围、用户故事、约束、接口和验收标准写成可以评审、拆分与追踪的规格。

最小规格至少回答：

- 为什么做，服务谁；
- 做什么，不做什么；
- 输入、输出和状态是什么；
- 哪些场景必须成功，哪些失败必须可见；
- 如何验证完成。

## Harness 约束执行

Harness 是围绕 AI 执行建立的工程系统：项目说明和上下文决定它知道什么，权限、工具和工作空间决定它能做什么，测试、Review、预算和退出条件决定结果怎样被检查。

目标与执行环境需要一起设计；清晰规格要能映射到任务和检查，执行过程也要能在失败时停止或回滚。

### 最小项目说明

`AGENTS.md` 或 `CLAUDE.md` 可以承载稳定的项目约定。文件应短到容易维护，并把运行命令、检查方式和禁止范围写具体。不同编程助手读取哪些文件、按什么层级合并，取决于自身实现；文件存在不代表一定被加载。

下面以 Astro / Starlight 文档仓为例，命令与本知识库一致：

```markdown title="AGENTS.md 的最小内容示例"
# 项目约定

- 正文放在 src/content/docs/，稳定图片放在 public/images/。
- 页面路径随文件路径变化；调整路径时检查导航与站内链接。
- 保留已有未提交变更，只处理当前任务涉及的内容。

## 运行与验收

- 本地开发：npm run dev
- 内容与类型检查：npm run check
- 生产构建：npm run build
- 文档交付前运行检查和构建，报告结果及未验证项。

## 边界

- 不把凭据写进正文、日志或提交。
- 不擅自删除验收项、扩大修改范围或发布站点。
- 图片需要替代文本，并在桌面和移动端检查排版。
```

业务细则、长篇 API 说明和完整范例按需链接出去。说明文件规定预期行为，实际执行权限还要由工具、沙箱和 CI 控制。

### 六种机制分别约束什么

| 机制         | 主要职责                     | 最小用法                                     |
| ------------ | ---------------------------- | -------------------------------------------- |
| 项目说明     | 稳定上下文与通用规则         | 写目录职责、运行命令、风格和禁止范围         |
| Skill        | 可复用的任务流程             | 把同类任务的输入、步骤和验收封装起来         |
| 命令入口     | 显式启动某个流程             | 用户选择执行审查、生成说明等任务             |
| Subagent     | 隔离任务上下文与职责         | 把代码探索或独立审查委派出去，返回结论和证据 |
| Plan Mode    | 在实现前理清路径             | 先分析范围、依赖、风险与验证，再进入修改     |
| 权限与 Hooks | 限制动作、在事件节点运行检查 | 限制写入和外部操作，自动触发格式或质量检查   |

Skill 既可能被自动匹配，也可能被显式调用；有些工具会把 Skill 和命令入口统一起来，不能机械地理解成“Skill 只能自动触发”。

Subagent 的核心价值是独立上下文和职责。Git worktree 隔离的是工作文件，两者需要分别配置；启用子 Agent 不代表文件自动隔离，也不代表任务适合并行。

Plan Mode 适合范围不清、跨模块、陌生代码或失败代价较高的任务。它能帮助先审查方案，但真正能否写文件、运行命令，仍由当前权限和工具实现决定。

### 权限与事件检查

权限通常可以按“允许、需确认、禁止”理解。下面是策略示例，并非可直接粘贴的配置文件：

| 策略  | 示例                                           | 判断依据                             |
| ----- | ---------------------------------------------- | ------------------------------------ |
| allow | 读取当前任务代码、查看差异、执行已知的本地检查 | 范围明确，副作用可控                 |
| ask   | 改依赖、调整验收语义、访问额外目录             | 可能改变环境或既有约定，需要另行判断 |
| deny  | 越权访问凭据、绕过验收、执行禁止的部署操作     | 超出任务的授权边界                   |

测试命令可能写文件、连接数据库或调用外部服务，不能因为名字叫 test 就当成只读操作。自动化流程没有人在场时，也要把需确认的情况转成停止或待处理状态。

Hooks 把检查放进工具生命周期，例如编辑后格式化、命令执行前检查危险参数、结束前提醒补齐验证。具体事件名、可拦截范围、失败退出码的含义都要按所用工具配置。提醒型 Hook 不等于强制门禁；发布前必须执行的检查应在受保护的 CI 中再次落实。

更完整的概念说明见 [Harness](/agent/harness/)；循环中的验收保护见 [Loop Engineering](/ai-programming/methodology/loop-engineering/#保护验收标准)。

## 规格工具怎么选

**要点**：先选择协作方式，再选择承载它的工具。新旧项目是参考维度，还要考虑谁拆任务、任务粒度、技术栈熟悉程度、审查成本和失败代价。

| 协作方式          | 人与 AI 如何分工                              | 适合条件                             |
| ----------------- | --------------------------------------------- | ------------------------------------ |
| AI 辅助规划与执行 | 人定目标并审查，AI 起草规格、拆任务、逐项实现 | 能把需求和验收写清，愿意持续核对产物 |
| 人主导拆解        | 人定依赖、接口和任务，AI 执行单个任务         | 系统约束多，需要细控顺序与变更范围   |
| 轻量小步协作      | 人定局部方案，AI 修改一小段，立即审查         | 对现状足够熟悉，增量可完整理解和验证 |

轻量协作也可用于熟悉的关键路径，但关键判断和必要验收仍要留下记录。陌生领域、影响面大或多人接力时，应增加显式规格与决策记录。

Spec-Kit 适合用规格串联完整产物；OpenSpec 擅长表达相对既有行为的变化。两者都可用于新旧代码仓，也都需要人工判断，并不分别等于“全自动”和“手动”。

### Spec-Kit

先固定工程原则，再明确需求、消除歧义、制定计划、拆解任务并实现。核心是让需求、方案和实现可以互相追踪；已有代码仓也可以逐个功能接入。

| 操作                 | 回答的问题                           | 主要产物或作用                                       |
| -------------------- | ------------------------------------ | ---------------------------------------------------- |
| constitution         | 哪些工程原则不可随意改变？           | 项目原则与治理约定                                   |
| specify              | 为谁解决什么问题，怎样验收？         | 功能规格、用户场景与验收条件                         |
| clarify              | 哪些歧义会影响实现？                 | 把澄清结论写回规格                                   |
| plan                 | 用什么技术方案实现？                 | 技术计划、研究结论、数据模型或接口契约               |
| checklist            | 需求是否清晰、完整、一致？           | 规格质量检查；不代表实现已经通过测试                 |
| tasks                | 实现顺序和独立验收单元是什么？       | 按依赖组织的任务清单                                 |
| analyze              | 规格、计划和任务之间有无冲突或遗漏？ | 一致性分析，不代替代码运行验收                       |
| implement / converge | 实现是否完整，差距如何收敛？         | 实现与验证；支持 converge 的版本会检查缺口并追加任务 |

典型产物位置如下；以实际初始化结果和安装版本为准：

| 路径                              | 职责                       |
| --------------------------------- | -------------------------- |
| `.specify/memory/constitution.md` | 跨功能复用的工程原则       |
| `.specify/templates/`             | 规格、计划和任务模板       |
| `specs/001-feature/spec.md`       | 某个功能的行为与验收       |
| `specs/001-feature/plan.md`       | 对应该功能的技术方案       |
| `specs/001-feature/tasks.md`      | 可执行任务、依赖与完成状态 |

例如“允许用户切换主题”，规格先说明默认主题、切换和持久化行为；计划再决定状态与样式如何实现；任务则拆成可验证的增量。不能让任务清单替代行为规格。

产物之间形成约束和追踪关系。规格变更后，应主动检查计划、任务、测试和实现是否需要同步；工具不会天然消除所有下游漂移。

[![规格产物关系：工程原则约束行为规格，规格细化为技术计划和任务，再由实现与验证证据反向核对](/images/ai-programming/notes/spec-artifacts.svg)](/images/ai-programming/notes/spec-artifacts.svg)

任务标为可并行之前，要确认无共享写入或尚未确定的接口依赖。勾选任务表示执行进度，完成结论仍要回到规格和测试。

初始化通常通过 `specify init` 完成，选择目标目录和编程助手集成。聊天中的入口可能是 `/speckit-…`、`/speckit.…` 或其他形式，按初始化输出和工具帮助选择，不能混用不同集成的命令。终端 CLI 与聊天入口也不是同一种执行环境。

### OpenSpec

偏重已有系统的增量变更：提出变更、实施并验证、归档结果。规格差异常用 `ADDED`、`MODIFIED`、`REMOVED` 表达，适合范围明确、需要控制修改面的小步演进。具体命令与工作流以所用版本为准。

| 路径                                               | 职责                                 |
| -------------------------------------------------- | ------------------------------------ |
| `openspec/specs/<domain>/spec.md`                  | 已归档的行为约定，仍需与实际代码核对 |
| `openspec/changes/<change>/proposal.md`            | 为什么修改、范围与影响               |
| `openspec/changes/<change>/design.md`              | 必要的技术决策                       |
| `openspec/changes/<change>/tasks.md`               | 实施清单                             |
| `openspec/changes/<change>/specs/<domain>/spec.md` | 本次新增、修改或删除的行为           |
| `openspec/changes/archive/`                        | 已归档变更及其上下文                 |

下面是一个主题设置的增量规格示例。假设既有行为是固定浅色主题，且存在准备移除的旧入口；删除某项要求前必须确认它确实存在并评估兼容性。

```markdown title="主题设置的增量规格示例"
## ADDED Requirements

### Requirement: 用户选择主题

系统 SHALL 允许用户切换浅色与深色主题，并保留用户选择。

#### Scenario: 刷新后保留选择

- **WHEN** 用户选择深色主题并刷新页面
- **THEN** 页面仍显示深色主题

## MODIFIED Requirements

### Requirement: 默认主题

系统 SHALL 在用户尚未保存选择时跟随系统主题。

#### Scenario: 首次访问

- **WHEN** 用户没有保存主题偏好且系统使用深色主题
- **THEN** 页面显示深色主题

## REMOVED Requirements

### Requirement: 旧版主题入口

**Reason**: 新的主题设置统一承载切换行为。
**Migration**: 旧入口跳转到新的设置入口。
```

`MODIFIED` 应写出更新后的完整要求和相关场景，不能只写“支持深色”。旧行为、修改理由和影响放进提案与差异记录，方便审查。`REMOVED` 还需要考虑迁移和调用方，而不是只删一行文字。

典型使用顺序是初始化 `openspec init`，探索问题、提出变更、审查提案与规格、实施、验证，最后归档并同步主规格。归档记录变更与行为约定，不等于代码已发布。

官方文档常用 `/opsx:explore`、`/opsx:propose`、`/opsx:apply`、`/opsx:archive` 表示操作；不同助手可能生成不同拼写。扩展的 `verify` 等入口也可能需要启用对应 profile。使用前检查初始化结果；不要因为归档动作可执行，就跳过实现验证。

多个变更可以分别组织在不同目录，但同时修改同一要求、共享接口或实现文件时仍然可能冲突，需要协调实施与归档顺序。

## 最小闭环

1. 写目标、非目标和验收标准。
2. 准备项目说明、参考实现和运行环境。
3. 拆成可独立验收的小任务。
4. 在约定的范围和权限内执行。
5. 用测试、构建、Review 和运行记录验收。
6. 把重复有效的经验提炼成规则或 Skill。

规格必须可以评审，计划必须可以验收。发现规格有误时先修正规格，再继续实现。

## 常见误区

- 只有规格，没有执行约束，AI 仍可能跑偏。
- 只有规则，没有清晰目标，执行可能一直偏离需求。
- 说明文档很长，却没有自动检查、预算和退出条件。
- 只检查能否编译，没有回到规格核对关键行为。
