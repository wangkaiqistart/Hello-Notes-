> **重点**：代码更容易生成以后，目标定义、架构取舍、验证和上线责任仍由工程师承担。持续成长依赖主动理解、独立判断和可复用的经验。

## 软件工程的重心变化

软件工程仍然要解决真实问题，交付可运行系统并承担长期责任。变化在于，实现动作可以交给模型，人需要组织上下文、工具和反馈，判断结果是否符合目标。

代码生成更快，会把瓶颈推向验证：错误也可能被更快地复制到多个模块。规格、架构决策、测试和运行记录因此成为与代码同样需要维护的产物。

## 三种需要持续积累的能力

| 能力       | 具体动作                       | 留下什么                              |
| ---------- | ------------------------------ | ------------------------------------- |
| 工作流设计 | 拆分阶段、任务、反馈和退出条件 | 任务卡片、检查流程、回滚步骤          |
| 工程判断   | 比较架构、范围、风险和长期成本 | 决策记录、失败案例、取舍理由          |
| 经验复用   | 把重复有效的方法提炼成规则     | Skill、模板、测试方法、文章和开源贡献 |

工具熟练度和技术栈深度仍然有价值，但需要能迁移到新工具和新问题上。工作年限的价值来自已经形成的判断与案例。

判断一项积累能否长期复用，可以问三件事：它是否需要真实场景判断，是否包含自己的案例与取舍，是否会在持续反馈中增长。背熟某个工具菜单，与能解释为什么选择它、何时放弃它，形成的是不同层次的能力。

## 学习中的两个风险

- **过度卸载思考**：每个问题都让 AI 先回答，自己失去形成问题模型和判断的机会。
- **只追求速度**：跳过读代码、写测试和定位根因，短期产出增多，长期理解逐渐欠账。

### 认知债与技术债

技术债关注实现与设计给后续维护带来的成本；认知债关注人对系统的理解落后于系统变化。代码即使能运行、风格整齐，也可能没有人说得清为什么这样设计、出了故障怎样恢复。

两者可能同时发生，但不能混为一谈。接收生成代码时，至少应能解释关键路径、状态变化、失败模式、验证证据和回退方式。只点击批准、没有形成理解，会让审查逐渐变成形式。

AI 会放大生成能力，也会加快复杂度积累。设计审查要关心未来修改是否困难，而不只看当前功能能否通过测试；高风险行为还可以补充不变量、属性测试或适用的形式化检查。

## 把学习设计成具体动作

**要点**：保留一部分需要自己建模、定位和解释的工作，再用 AI 提供反馈。练习的困难应服务于理解，不能把长时间无方向试错当成唯一的成长方式。

| 学习环节     | 自己先做什么                       | 怎样借助 AI                            | 留下什么证据                 |
| ------------ | ---------------------------------- | -------------------------------------- | ---------------------------- |
| 学新概念     | 写出自己的理解和一个疑问           | 要求举反例、比较两种方案，检查解释漏洞 | 用自己的话重述概念与适用边界 |
| 学新 API     | 读签名、写最小调用并预测输出       | 追问参数、错误行为和替代接口           | 可运行示例与边界输入         |
| 排查错误     | 读报错、画调用链、提出一个假设     | 请它评估假设或提示下一项证据           | 复现、实验、根因和回归记录   |
| 接收生成代码 | 解释关键路径，找一个可能失败的输入 | 让它质疑设计并比较修正方案             | 取舍理由、失败用例与验证结果 |
| 复习         | 关掉答案，重新解释或实现最小版本   | 让它根据自己的回答继续追问             | 无提示时仍能完成的解释或实现 |

刚接触某个领域时，先独立尝试一个小问题，再问概念和提示；熟悉领域后，重点守住架构、复杂度、兼容性和系统风险。两者都要避免产出速度长期超过理解速度。

可以每周选择一个小任务练习：先写问题模型，独立定位一个错误，再让 AI 提供反例，最后把修复讲给别人听。结对审查或导师反馈能帮助发现自己的解释盲点，不必每次都重新独自摸索。

### 用三层追问检查是否真正理解

1. **是什么**：这段实现解决什么问题，输入、输出和状态是什么？
2. **为什么**：为什么选这个方案，比较并否决过什么？
3. **条件变了怎么办**：流量增加、依赖失败、需求变化时，哪个假设先失效？

如果只能复述实现、不能推演变化，应回到设计与实验补理解。学习效果需要通过独立解释、迁移和后续表现检查；不能只凭一次任务变快，就断言能力已经提高。

## 个人能力闭环

先独立写出问题模型和候选方案，再让 AI 补充反例；对关键模块保留设计、实现和验证记录。审查生成代码时，要能解释边界、失败模式和验证证据。

每完成一个任务，检查三个问题：

1. 这次自己做出的关键取舍是什么？
2. 哪个步骤可以变成规则、模板或 Skill？
3. 哪份证据能让别人复查结果？

决策记录可以保持简短：当时的约束、比较过的方案、选择理由、预期风险，以及后来发生了什么。隔一段时间复查预测和实际差异，才能把经验转成判断，而不是只留下成功结论。

文章、可复用示例和开源贡献可以承载这些经验。公开反馈有助于校正理解与积累协作信誉，但价值仍取决于问题是否真实、证据是否可检查，以及内容能否被别人复用。

## 面试与能力表达

表达 AI 协作经历时，要把自己的判断和验证讲清楚：

| 表达层次   | 需要说明的内容                           |
| ---------- | ---------------------------------------- |
| 执行       | AI 完成了哪些工作，自己负责哪些环节      |
| 判断       | 为什么这样拆解、选型或设计，否决过什么   |
| 验证       | 如何发现第一版的问题，用什么证据确认修正 |
| 结果与责任 | 实际结果、未解决限制，以及自己承担的职责 |

例如可以这样组织一段真实经历：“我让 AI 起草日期解析实现，自己明确了非法日期必须拒绝的契约。审查发现它会把不存在的日期滚动到下个月，我补了回归用例，修正后检查合法日期、闰年和调用方行为。”

这个示例展示表达结构。实际叙述只使用自己做过且能解释的取舍，性能收益、故障影响和测试结果都应有记录，不能用漂亮的数字代替证据。
