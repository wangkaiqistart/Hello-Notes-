<Aside type="tip" title="一句话结论">
  AI 编程改变了代码的生产方式，但没有改变程序员解决问题、创造业务价值的目标。代码可以交给 AI
  生成，目标、判断、验证和责任仍由工程师负责。
</Aside>

## 程序员的目标没有变

程序员的价值不在于写了多少代码，而在于能否用可靠的方式解决问题、交付功能并产生业务价值。代码只是实现手段，AI 是新的技术杠杆：它降低了实现成本，也提高了对问题定义和工程判断的要求。

## AI 编程带来的三层变化

这套工作链路可以概括为：

> 明确目标 → 提供上下文 → 组织 AI 执行 → 验证结果 → 对交付负责

AI 可以生成代码、补充测试、分析日志和执行重复性修改，但不能替工程师决定业务边界，也不能承担上线后的责任。

## 工程师真正需要保留的能力

| 责任环节 | 工程师要做什么                     | AI 可以协助什么                |
| -------- | ---------------------------------- | ------------------------------ |
| 定义问题 | 明确目标、范围、规则和验收标准     | 整理需求、补充疑问、梳理上下文 |
| 做出判断 | 选择方案，权衡成本、风险和可维护性 | 对比方案，提供实现建议         |
| 验证结果 | 检查业务正确性、工程质量和上线影响 | 生成测试、运行检查、分析日志   |
| 承担交付 | 决定是否上线，并对结果负责         | 执行修改、整理记录、沉淀资产   |

工具熟练度会随产品变化，长期能力则来自三件事：理解业务，做出取舍，验证结果。把项目规则、决策记录、Skills、测试用例和故障经验沉淀下来，才能让一次交付变成下一次工作的起点。

## 方法论如何分工

这些概念不必混在一起记，可以按它们解决的问题理解：

| 方法                           | 解决的问题                | 关键作用                                     |
| ------------------------------ | ------------------------- | -------------------------------------------- |
| SDD（Spec-Driven Development） | AI 不清楚要做什么         | 用规格明确目标、范围、规则、边界和验收标准   |
| Harness Engineering            | AI 不知道如何在边界内执行 | 用规则、工具、权限、Hooks 和检查机制约束执行 |
| Context Engineering            | AI 缺少有效信息           | 管理项目知识、任务上下文和信息范围           |
| Test-Driven AI                 | AI 产出难以判断           | 用测试和运行结果验证行为是否符合预期         |
| ReAct、TAO 等 Agent 框架       | 如何完成多步自主任务      | 适合 Agent 应用，不是通用研发流程主轴        |

## 为什么是 SDD + Harness

SDD 和 Harness 是互补关系：

- **SDD 解决“做什么”**：把需求变成可审查、可共享、可执行的规格。
- **Harness 解决“怎么做”**：给 AI 配置项目规则、工具、权限和反馈机制，让执行保持在合理边界内。
- **工程师解决“是否正确”**：通过测试、Review、构建和实际运行验证结果，并决定是否交付。

> 规格明确目标 → Harness 约束执行 → 工程验证结果

只写规格，执行可能失控；只配约束，方向可能一开始就错。两者结合，才形成从目标到交付的完整闭环。

## 最后留下的判断

AI 编程时代，工程师要训练的不是某个工具的熟练度，而是把问题想清楚、组织 AI 做正确、验证结果并稳定交付的能力。工具会变化，但这套能力可以跨工具、跨项目和跨技术栈迁移。
