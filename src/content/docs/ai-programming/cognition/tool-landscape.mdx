> **重点**：先定位问题在哪一层，再挑选工具。模型变强，不会自动解决权限、协作、验证和交付问题。

## 七层架构

| 层           | 解决的问题             | 典型内容                              |
| ------------ | ---------------------- | ------------------------------------- |
| 模型层       | 谁负责理解、推理和生成 | Claude、GPT、Gemini、开源模型         |
| 工具层       | 模型能操作什么         | IDE、终端、文件、浏览器、SDK          |
| 配置与约束层 | AI 必须遵守什么        | `AGENTS.md`、`CLAUDE.md`、权限、Hooks |
| 协作机制层   | 复杂任务如何分工       | Plan、Subagent、Worktree、Review      |
| 协议与生态层 | 如何连接外部能力       | MCP、CLI、插件、集成协议              |
| 工作流层     | 什么时候运行、如何验收 | CI/CD、事件触发、测试、发布、回滚     |
| 方法论层     | 如何稳定地产生结果     | SDD、Harness、Loop Engineering、TDD   |

下图从模型层向上排列，再归为工具基础、工程能力和杠杆价值。分层用来区分职责，同一工具可能覆盖多个层级。

## 选型顺序

1. 描述任务、验收条件和失败代价。
2. 判断瓶颈属于生成、上下文、权限、协作、验证还是部署。
3. 筛选能留下中间产物和验证记录的工具。
4. 用最小真实任务验证效果，再扩大使用范围。
5. 保持任务模型和验收标准稳定，使工具可以替换。

## 技术趋势与证据核验

观察新工具时，要先分清它是模型、编程工具、Agent 底座、协议还是业务应用，再判断它改善了哪一层能力。

| 观察维度 | 核验问题                                           |
| -------- | -------------------------------------------------- |
| 目标用户 | 面向个人开发者、协作团队、平台维护者还是终端用户？ |
| 控制能力 | 只是生成内容，还是补上权限、协作、验证与运维？     |
| 可复现性 | 是否有源码、明确版本、运行步骤和失败案例？         |
| 时间边界 | 数字、版本和生态支持截止到哪一天？                 |
| 使用成本 | 成功率、延迟、调用成本和维护成本如何？             |

验证应从官方信息逐步走到自己的真实任务，记录失败和成本后再做项目决策。

## 容易误判的信号

- Star 数不能证明运行稳定性。
- Demo 成功不能证明复杂项目可交付。
- 模型基准分不能证明工具调用可靠。
- 官方集成不能证明适合所有团队。
- 插件数量不能替代权限、退出和回滚规则。

同一模型在不同上下文、权限和验证条件下，可能产生完全不同的工程结果。选型应围绕可验证的改善展开。

## 三种场景怎样组合各层能力

**要点**：七层架构用于定位职责。实际工作需要把几层连起来，而不是每层都安装一个工具。

| 场景                 | 先解决的问题                   | 怎样组合能力                                             | 怎样验收                                 |
| -------------------- | ------------------------------ | -------------------------------------------------------- | ---------------------------------------- |
| 新增一个模块         | 目标、接口和失败行为是否明确？ | 规格与任务拆分，结合项目规则、编码工具和回归检查         | 核对契约、正常与异常路径、相关调用方     |
| 修改陌生的大型代码仓 | 入口、依赖和隐藏约束在哪里？   | 代码检索与隔离探索，形成可复查的调用链，再规划小范围修改 | 核对真实路径、兼容性、变更范围与回归     |
| 接入 CI 自动处理任务 | 谁触发，能操作什么，怎样交接？ | 非交互执行、最小权限、受保护检查、状态记录和失败通知     | 核对指定版本的结果、预算、退出与人工放行 |

非交互运行还要考虑凭据如何提供、命令是否会等待输入、工具输出怎样保存，以及失败后是否重复产生外部副作用。把交互式助手搬进 CI，不会自动得到可靠工作流。

MCP 用于以统一方式连接工具与数据能力；A2A 关注不同 Agent 之间的协作交互。两者职责不同，也不意味着所有任务都需要这些协议。已有 CLI 或 API 能清楚完成目标时，应比较接入成本、权限和可观测性再决定。
