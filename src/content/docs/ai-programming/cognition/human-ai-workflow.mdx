> **重点**：AI 承担执行，人负责目标、边界、关键取舍和最终放行。每个任务都要有输入、验收和失败处理。

## 六个阶段的分工

| 阶段 | AI 适合做                        | 人需要负责                     |
| ---- | -------------------------------- | ------------------------------ |
| 需求 | 补充场景、整理验收标准、发现遗漏 | 用户价值、范围、优先级         |
| 设计 | 生成候选方案、比较资料、画草图   | 架构边界、长期成本、关键决策   |
| 开发 | 生成代码、测试、机械重构         | 核心路径、异常语义、实现取舍   |
| 测试 | 生成用例、执行回归、归纳失败     | 风险边界、测试可信度、放行判断 |
| 部署 | 生成脚本、检查配置、执行标准步骤 | 上线时机、权限、回滚决策       |
| 运维 | 汇总日志、定位线索、提出方案     | 故障定级、业务影响、处置责任   |

## 从准备到交付

1. **建立地基**：准备日志、监控、HTTP、API 规范、代码规范和安全扫描。
2. **冻结边界**：写目标、非目标、验收标准、方案和模块接口。
3. **拆小任务**：按依赖顺序形成可以独立提交和验收的任务。
4. **受控执行**：AI 按任务工作，人检查方向、边界和变更范围。
5. **分层验证**：根据风险执行单元、集成、故障、性能和端到端验证。
6. **交付沉淀**：部署、监控、回滚、Review、复盘并更新规则和 Skill。

## 哪些任务适合自动执行

**重点**：自主程度取决于验收是否可靠、错误代价是否可控。规则明确的迁移与改造，通常比需要不断发现需求的探索更容易形成稳定循环。

| 判断维度   | 可以扩大自动化的信号                 | 应收紧自动化的信号               |
| ---------- | ------------------------------------ | -------------------------------- |
| 目标与规则 | 输入输出、兼容约束与错误语义明确     | 需求互相冲突，目标仍需探索       |
| 参考依据   | 有可信的旧实现、接口契约和代表性样例 | 只有演示截图或模糊描述           |
| 反馈质量   | 能重复运行并自动判定关键行为         | 只能靠“看起来正常”或模型自评     |
| 工作环境   | 依赖可复现，权限与修改范围有限       | 共享状态复杂，操作影响范围不确定 |
| 失败处理   | 错误易发现，可停止、回退或隔离       | 高代价、不可逆，失败难以及时发现 |
| 人工检查   | 有明确交接点和责任人                 | 无人理解中间产物，只在最后扫一眼 |

例如，按明确映射批量替换 API，并用既有回归检查兼容性，可以交给受控循环。设计全新产品的交互、裁定业务取舍或修改难以复现的一致性机制，需要更密集的人工判断。

“改造”也不是天然简单：历史行为没有写清、旧测试薄弱或依赖复杂时，应先补契约、测试和探索结果，再放大执行范围。选择哪种工具，不能替代这一步判断。

## 任务卡片

每个任务至少包含：

- 目标、非目标和验收标准；
- 前置契约、依赖和参考实现；
- 需要修改的模块与文件范围；
- 正常、异常和边界场景；
- 验证命令、预期结果和运行记录；
- 失败处理、退出条件和回滚方式。

接口和依赖尚未冻结时，不适合同时展开多个互相依赖的任务。一次协作应留下目标、方案、变更记录、测试结果和运行证据，便于复查和继续工作。

### 从需求拆到可交接任务

先围绕可观察行为划分，再为每个行为补实现依赖。不要只按“数据库、后端、前端各做一遍”拆分，却一直没有能验证的完整路径。

1. 写一个能验收的用户场景及其异常分支。
2. 找出输入输出、状态变化和必须先确定的接口。
3. 将其拆成小增量，每项写清依赖和检查方法。
4. 先完成公共契约与基础能力，再推进独立分支，最后集成验收。
5. 每项结束时更新进度、证据和下一项需要的上下文。

并行应建立在依赖和写入范围明确的基础上。两个 Agent 都需要修改同一个共享接口时，先确定接口或改成串行，通常比事后修冲突更容易控制。

## Review 的三个问题

1. 是否满足规格，关键行为是否符合验收标准？
2. 是否引入未授权的范围、权限或数据风险？
3. 测试是否覆盖真正容易出错的行为，失败能否被发现？

## 测试通过之后还要确认什么

测试结果只覆盖已经编码的条件。依赖替身、固定数据、单机环境和短时间运行，都可能隐藏真实问题。

| 当前证据         | 能支持的结论                     | 仍需核对                                 |
| ---------------- | -------------------------------- | ---------------------------------------- |
| 单元测试通过     | 被测试的逻辑在这些输入下符合断言 | 实际依赖、完整路径、断言是否遗漏关键行为 |
| 构建通过         | 当前代码能完成构建               | 运行配置、权限、数据与环境兼容性         |
| 集成或端到端通过 | 指定环境中的选定流程成立         | 故障、并发、负载与未覆盖场景             |
| 线上指标正常     | 观察窗口内选定指标未出现异常     | 低频故障、长期效果、监控本身的盲点       |

从规格到拆解、实现、测试、部署，每一环的错误都可能影响最终结果。不能用某个环节的高成功率代表整条链可靠，也不能不加条件地相乘几个经验百分比作为结论。

验证强度应跟随失败代价，优先补最薄弱的环节。重点保护验收规则、区分本地反馈与外部检查，具体做法见 [Loop 的验收保护与分层检查](/ai-programming/methodology/loop-engineering/#保护验收标准)。

## 何时停止自动执行

- 需求仍有多个互斥解释；
- 操作超出已确认的权限、范围或回滚能力；
- 测试通过，但没有覆盖真实风险；
- 连续尝试却没有取得新证据；
- 成本、延迟、轮数或失败率超过预算。

自动化程度取决于错误能否及时发现、影响能否控制以及结果能否回滚。
