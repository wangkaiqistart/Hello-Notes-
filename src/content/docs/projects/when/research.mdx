> **结论**：延时投递需求真实且广泛，但现有方案往往绑定消息中间件、绑定应用进程或偏向 Cron 调度，独立、可集群、可插拔的延时服务仍有清晰空间。

## 典型场景

订单超时、支付回查、优惠券到期、定时通知、延迟重试、业务补偿和异步回调都需要“到时间再投递一次消息”。

## 方案边界

| 方案                                 | 优势                  | 局限                                 |
| ------------------------------------ | --------------------- | ------------------------------------ |
| Kafka / RocketMQ / Pulsar / RabbitMQ | 已有持久化和消费体系  | 延时能力绑定特定 MQ                  |
| 应用内 SDK                           | 接入简单、开发快      | 随应用生命周期，难以统一治理和高可用 |
| 任务队列 / 调度平台                  | 适合任务执行和 Cron   | 不一定适合高吞吐消息投递             |
| 云厂商托管服务                       | 运维成本低            | 平台绑定、网络和数据边界受限         |
| 独立延时服务                         | 统一接入、可插拔 Sink | 需要自己解决存储、集群和故障恢复     |

## 算法观察

常见实现包括数据库轮询、优先队列、时间轮、分层时间轮、Redis 有序集合和消息中间件的延时主题。选型要同时看时间跨度、精度、吞吐、持久化、扩展和故障恢复。

## When 的切入点

- 外部接入使用通用 HTTP；
- 内部使用强类型、高效的 gRPC；
- Redis 保存消息真源，时间轮承担调度加速；
- ETCD 管理节点、选主和时间轮分配；
- 下游通过 Sink 插件扩展。
