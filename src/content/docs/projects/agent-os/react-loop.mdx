ReAct 是 AgentOS 的第二块核心能力，也是整个 Agent 最关键的一段代码。这节讲四件事：ReAct 是什么、动手前该想清楚什么、代码怎么写、做完怎么验。它依赖上一节的 Provider——每转一圈都要通过 Provider 调一次大模型。当前项目的技术栈是 JDK 21、Spring Boot 4.1.2 和 Spring AI 2.0.2；下面只在接口和上下文机制不同的地方按 AgentOS 进行替换。

## 一、ReAct 是什么，干嘛用的

一句话：ReAct 就是让大模型像人做事一样，在一个循环里反复“想一步、做一步、看结果”，直到把事办成。

单独调一次大模型，就是个 chatbot——你问一句、它答一句，完事。但很多事一句话答不了，比如“看看今天天气，帮我决定穿什么”，模型得先去查天气、拿到结果、再根据结果给建议。

ReAct 干的就是把“想—做—看”串成一个循环：模型想下一步该干嘛、调个工具去做、拿到结果看一眼，不够就再来一轮，够了就给最终答复。这个模式叫 ReAct（Reasoning + Acting），2022 年提出来，现在是事实标准，Claude Code、Cursor、LangChain 跑的都是它。

一轮里的动作是固定的三步：

- **Reason / 想**：想下一步做什么；
- **Act / 做**：调一个工具执行；
- **Observe / 看**：拿结果，并回到上下文。

![AgentOS ReAct 执行循环：输入进入 Reason、Act、Observe，工具结果回到上下文，边界检查后完成或继续](/images/projects/agent-os/react-loop.svg)

还没完成，就带着新状态回到 Reason；这轮没有工具调用，就返回最终响应；转够最大轮数（默认 10），就强制结束。

什么时候停？看模型这一轮的反应：它没提出要调工具，就说明它觉得能给最终答复了，循环返回结果；万一它一直要调工具停不下来，就靠“最大轮数”兜底，转够了强制收尾。

放回 Agent 整体：ReAct 是那个“大脑循环”，它自己不调模型、也不执行工具，而是指挥——想的时候通过上一节的 Provider 调一次大模型，做的时候把工具交给后面会讲的 ToolExecutor。

## 二、动手前先想清楚几件事

有个反直觉的地方：它是 Agent 的灵魂，但主循环的代码其实很短，就几十行。难的不是写个 `while` 循环，而是循环里要照顾的那些边界。所以动手前先把三件事定下来：职责怎么拆、为什么自己写、有哪些坑。

第一，把职责拆干净。循环本身只该做一件事——调度。它负责转圈、判断该不该停、把每轮的结果攒起来。至于每轮要拼的 Prompt、要调的模型、要执行的工具，全都交出去，让专门的模块干。循环里塞的东西越少，它越好读、越不容易出 bug。

| ReActLoop 负责 | 交给别人 |
| --- | --- |
| 一圈圈转（调度） | 拼上下文 → `PromptBuilder` |
| 判断这轮该不该停 | 调大模型 → `ProviderService` |
| 把响应和结果累积到 Session | 执行工具 → `ToolExecutor` |

第二，为什么自己写，不用框架现成的循环。Spring AI 这类框架都带现成的 Agent / 循环封装，拿来就能跑。但循环恰恰是 Agent 最需要自己掌控的地方——什么时候停、工具失败了怎么办、上下文太长了怎么压、哪几步想换个模型，这些都得能自己调。用框架的黑盒，这些就动不了。所以核心阶段我们自己写这几十行，把控制权攥在手里。当前 AgentOS 直接调用 `ChatModel`，由自己的 `ReActLoop` 控制循环，不再让 `ChatClient` 的另一套 Advisor 循环接管流程。

第三，几个坑，提前想到。这块最容易出事的就那么几处：

- 不设轮数上限，模型可能反复要调工具，陷进死循环下不来；
- 不管上下文长度，转几轮 context 就撑爆了（每次调模型都把全部历史带上，越滚越大）；
- 每轮不把模型响应和工具结果累积回 Session，事后就没法审计，下一轮也接不上前一轮。

这三条不是写完再补，是设计时就得定死的。想清楚了其实就几句话：循环短、职责拆出去、自己掌控、边界（停止 / 错误 / 上下文）提前定。

## 三、代码怎么写

拆成三个模块，各干各的：`ReActLoop` 管调度，`PromptBuilder` 管拼上下文，`ToolExecutor` 管执行工具。调大模型用的是上一节的 `ProviderService`。

一轮的流转是这样：

![ReActLoop 控制流：模型调用后判断工具请求，分别进入完成分支或工具执行、结果保存与下一轮](/images/projects/agent-os/react-control-flow.svg)

每轮把模型响应和工具结果都追加回 Session，转够最大轮数强制收尾。

先看主角 ReActLoop。原课件输入是一个 Session（存着这次对话的全部状态）加上用户这句话，输出是最终响应。当前 AgentOS 将 Turn 的租约、截止时间和审计关联放在 `TurnContext`，Session 仍负责保存会话消息；骨架长这样：

```java
TurnResult run(TurnContext turn, List<Message> messages) {
    List<Message> history = List.copyOf(messages);

    for (int i = 0; i < turn.profile().maxIterations(); i++) { // 默认 10，防死循环
        turns.renewLease(turn);

        ProviderRequest request = new ProviderRequest(
                turn.profile(),
                history,
                toolRegistry.allowedCallbacks(turn),
                Map.of("turnContext", turn),
                turn.deadline(),
                new CallCorrelation(turn.sessionId(), turn.turnId(), i));

        ProviderResult result = providerService.call(request);
        ChatResponse response = result.response();
        sessionMessages.appendModel(turn, response); // 累积，可审计

        if (!response.hasToolCalls()) {
            return turns.complete(turn, response); // 没有工具调用，收尾
        }

        Prompt prompt = promptBuilder.currentPrompt(turn, history, request.tools());
        ToolExecutionResult execution = toolExecutor.execute(prompt, response);
        sessionMessages.appendToolDelta(turn, execution.conversationHistory());
        history = execution.conversationHistory();
    }

    return turns.stopAtMaxIterations(turn);
}
```

一行行看它在干嘛：

- `for (i < turn.profile().maxIterations())` ——这就是“最大轮数”的兜底，默认 10。循环不是无限转的，转够就退出，死循环在这拦住；
- `promptBuilder.currentPrompt(...)` ——把这一轮要发给模型的内容拼好，下面细讲；
- `providerService.call(request)` ——通过上一节的 Provider 调一次大模型，`ProviderRequest` 带上 `sessionId`、`turnId` 和 `iteration`，供 `llm_calls` 审计关联；
- `sessionMessages.appendModel(...)` ——先把响应存回 Session 再说，这样每一轮都留了痕迹，事后能审计；
- `if (!response.hasToolCalls()) return` ——模型这轮没要调工具，说明它能给答复了，直接返回，循环结束；
- `ToolExecutor` ——模型要调工具，就交给 `ToolExecutor` 执行，结果再存回 Session，然后进下一轮。注意执行是 `ToolExecutor` 干的，不是这里，也不是 Provider 自动干的。

配角一：PromptBuilder。每轮开始，它把四部分按顺序拼成一段 Prompt：system prompt（角色设定 + 启动信息 + Skill，末尾附上当前日期时间——模型自己不知道今天几号，后面定时场景里的“今天”全靠这一行）、长期记忆（Memory 模块提供的跨会话记忆，没开就跳过）、会话历史（只留最近 N 轮，默认 20，超了就截断——这是上下文过长的解法）、当前可用的工具列表。

注意“长期记忆”和“会话历史”是两码事，别混在一起说：长期记忆是跨会话都在的东西，会话历史只是这一次对话到目前为止的往来记录。拼 Prompt 的逻辑全在这，循环那边不用操心。当前项目还要求按完整 Turn 截断历史，不能把助手的工具请求和对应的工具结果拆开。

配角二：ToolExecutor。从工具表里找到模型要调的那个工具，先过一道沙箱 / 白名单检查，再执行，把结果包成 `ToolExecutionResult` 返回，同时记一条调用日志——成功要记、失败也要记，`tool_invocations` 表本来就有 success / error_message 两列，跟上一节 Provider 的审计是同一个口径：一次工具调用不管成没成，事后都得能查到。

工具执行只在这一个地方发生——这也是上一节为什么要关掉 Spring AI 自动执行的原因：执行权必须收在这里，不能有第二条路。当前 Spring AI 2.0 的实现使用容器注入的 `ToolCallingManager`，由 `ToolExecutor` 调用 `executeToolCalls(...)`，再进入 `GovernedToolCallback`；不能在执行器里自行 `builder().build()` 创建第二个 Manager。

![AgentOS 工具调用链：ReActLoop 经 ProviderService 和 ChatModel，由 ToolExecutor 调用注入的 ToolCallingManager，进入受治理回调](/images/projects/agent-os/react-tool-chain.svg)

编排者 AgentService，这节一并交付。循环之上还差薄薄一层：三种触发源（CLI、Web、定时）最终都调同一个 `AgentService.process`，它是一次处理的编排者。当前项目的上下文不再使用原课件中的 `ProfileContext` / `ThreadLocal`，而是把 `TurnContext` 放进 Spring AI `ToolContext`，由工具按请求读取。

当前入口的骨架仍然和课件一样：取得配置，启动一次处理，结束时持久化并释放本轮资源；只是把原来的 ThreadLocal 清理替换成 Turn 租约的收口：

```java
public TurnResult process(AgentRequest request) {
    TurnContext turn = turnService.start(request);
    try {
        TurnResult result = reActLoop.run(turn, request.messages());
        sessionManager.save(turn.session());
        return result;
    } finally {
        turnService.finish(turn);
    }
}
```

供给者 ContextLoader，也归这节。PromptBuilder 的第一部分（Bootstrap 三件套 + `AGENT.md` / `SKILL.md`）由它提供：按 Agent 配置读取对应文件、拼成文本。两条铁律：每次组装 Prompt 都重新读文件、不缓存（用户改完立即生效）；显式引用的文件缺失要报错、Bootstrap 缺失至少 WARN——静默跳过会造成“人格悄悄丢了”这种最难查的软故障。

有几样先别做。工具并行调用、Agent 之间互相委托、流式输出、上下文压缩，这些核心阶段都先不做。上下文先用“只留最近 N 轮”这种简单办法顶着，够用就行，压缩留到扩展阶段。

本节交付物：

- **代码**：`ReActLoop`、`PromptBuilder`、`ToolExecutor`、`AgentService`、`TurnContext`、`ContextLoader`、`ToolInvocation` 实体与 `ToolInvocationRepository`；
- **测试**：`ReActLoopTest`、`PromptBuilderTest`、`ToolExecutorTest`、`AgentServiceTest`、`ContextLoaderTest`；
- **表**：`tool_invocations`（含 `success` / `error_message` 列，手工建表脚本）；
- **约定**：最大轮数默认 10；历史截断默认 20 轮；Prompt 末尾附当前日期时间。

当前 Java 仓库仍是工程骨架，上述清单是本节的实现目标和验收锚点，不表示业务类已经全部完成。

## 四、验收 harness：把验收标准变成可执行的测试

这节的东西全部不碰网络——`ProviderService`、工具、文件系统都能 mock 或用临时目录，所以 harness 全是单测，`mvn test` 秒级跑完。五个测试类对应五个交付物：

| 测试类 | 覆盖的验收点 |
| --- | --- |
| `ReActLoopTest` | 无工具调用一轮收尾；有工具调用则执行并回填进下一轮；转满最大轮数强制停；每轮响应和工具结果都累积进 Session |
| `PromptBuilderTest` | 四部分顺序正确；历史超 N 轮被截断；system prompt 末尾含当前日期时间 |
| `ToolExecutorTest` | 成功写审计 `success=true`；失败也写 `success=false` 带原因，异常不吞；只调用注入的 `ToolCallingManager` |
| `AgentServiceTest` | 三种入口共享处理服务；处理结束和异常路径都释放租约；不依赖 `ThreadLocal` |
| `ContextLoaderTest` | 改文件后下一次 build 立即读到新内容（无缓存回归）；Skill 引用缺失报错、Bootstrap 缺失 WARN |

两个最值钱的回归测试写出来：模型一直要调工具，转满最大轮数强制停；以及处理中抛异常时，租约和 Turn 状态都必须正确收口。离线 harness 全绿后，再接一次真实模型 Demo。

第一个测试守住死循环兜底：

```java
@Test
void 模型一直要调工具_转满最大轮数强制停() {
    when(providerService.call(any()))
            .thenReturn(providerResultWithToolCall(httpGetCall)); // 每轮都要调工具

    TurnResult result = loop.run(turnWithMaxIterations(10), List.of(userMessage("查天气")));

    verify(providerService, times(10)).call(any()); // 恰好 10 轮，一轮不多
    assertEquals(TurnStatus.MAX_ITERATIONS, result.status());
}
```

第二个测试守住异常路径：租约或 Turn 状态没有在 `finally` 中收口，下一次复用同一会话时就可能被错误地当成仍在运行。

```java
@Test
void 处理中抛异常_也必须释放租约() {
    when(reActLoop.run(any(), any())).thenThrow(new RuntimeException("boom"));

    assertThrows(RuntimeException.class, () -> agentService.process(request));
    verify(turnService).finish(any());
}
```

## 五、做完怎么验

harness 全绿后，剩下的人工确认：

- **Demo 一（每日天气）**的对话版（问天气、给穿搭建议）用真模型跑通一次：多轮对话里，Agent 调了 `http_get` 工具、拿到数据、给出建议；
- 循环是自己实现的，没用框架现成的 Agent 封装（code review 确认，测不出来）；
- 其余验收点——死循环兜底、累积、截断、失败审计——已由 harness 覆盖，`mvn test` 绿即打勾。

ReAct 要和上一节的 Provider 一起，才撑得起 Demo 一。所以这块跑通的标准很直接：Demo 一能从头到尾完整走下来。
