## 一、Agent 在技术上是什么

Agent 是一个能够感知环境、根据目标选择下一步行动、执行动作并利用反馈继续迭代的程序。

```text
Agent = LLM + Tools + Memory + Loop + Environment
```

这个公式是理解 Agent 的方法，不是固定的实现接口。Agent 这一类程序早于语言模型：强化学习系统、游戏 NPC 和自动化控制程序同样可以具备感知、决策、行动和反馈循环。LLM 只是降低了实现自然语言决策的门槛。

单次模型调用更接近 chatbot：输入一次，返回一次。把模型放进能够持续处理状态的循环，让它根据工具结果和环境变化继续选择下一步，系统才具备 Agent 的执行特征。

在 AgentOS 中，这五个组件的职责如下：

| 组件            | 作用                                     | AgentOS 的承载关系                                      |
| --------------- | ---------------------------------------- | ------------------------------------------------------- |
| **LLM**         | 根据任务和状态选择工具或形成回答         | ProviderService 按名称选择 ChatModel，返回 ChatResponse |
| **Tools**       | 读文件、请求服务、查询数据或执行受控操作 | ToolRegistry 管理 ToolCallback；ToolExecutor 统一执行   |
| **Memory**      | 保存会话过程，并按需复用跨会话事实       | MemoryService 汇集会话记忆和长期记忆                    |
| **Loop**        | 根据模型和工具结果继续、结束或中断       | ReActLoop 管理迭代，AgentService 协调轮次               |
| **Environment** | 提供交互对象，同时限制能接触的资源       | 工作区、外部服务、凭证和 Sandbox 形成运行边界           |

## 二、五个组件，撑起一个 Agent

模型通过工具作用于环境，工具结果回到 Memory 和下一次 Prompt，再影响下一步决策。组件可以替换，但职责不应因为替换模型或存储就全部挪进循环。

[![LLM、Tools 和 Memory 由 Loop 协调，工具在受控 Environment 中执行，结果进入下一次模型决策](/images/projects/agent-os/foundations-components.svg)](/images/projects/agent-os/foundations-components.svg)

_重点看结果如何回到下一次决策；点击图片可查看大图。_

Agent 定义位于 `.AgentOS/agents/<name>/AGENT.md`：frontmatter 派生 Profile，决定 provider、model 和工具集合；正文提供任务指令。全局连接在 `application.yaml`，聊天模型由 Agent 显式选择，具体配置见 [Provider 原理与实现](/projects/agent-os/provider/)。

## 三、Loop：Agent 的灵魂

ReAct 是 Reason、Act、Observe 的循环：模型根据当前状态决定下一步，运行时执行工具并取得观察结果，再把新状态交回模型。运行时不需要把模型的内部推理过程写入日志，应该记录实际响应、工具请求、工具结果和结束状态。

一次轮次的基本过程是：

1. **开始轮次**：确认 Agent 和会话，取得会话租约，创建轮次记录和截止时间。
2. **构造 Prompt**：组合 Agent 指令、Bootstrap、Skill 元数据、长期记忆、近期完整轮次和当前用户消息；工具定义放在请求选项中。
3. **请求模型**：ProviderService 选择 ChatModel，完成一次模型请求并记录调用审计。
4. **判断输出**：没有工具调用时保存助手消息并结束；有工具调用时交给 ToolExecutor。
5. **执行并回填**：ToolExecutor 调用注入的 `ToolCallingManager.executeToolCalls(prompt, response)`，取得工具结果及完整历史。
6. **继续或结束**：`returnDirect()` 为 true 时直接返回；否则以 `conversationHistory()` 继续下一次请求。达到上限、超时、取消或租约失效时终止。

`conversationHistory()` 已包含原消息、助手的工具请求和工具响应，不应手工重复追加同一组消息。一次响应请求多个工具时，只有它们全部声明直接返回，`returnDirect()` 才为 true。

### 循环还要控制什么

| 控制项                     | 约束对象                                           |
| -------------------------- | -------------------------------------------------- |
| `settings.max_iterations`  | 一个轮次最多进行多少次模型推理                     |
| `spring.ai.tools.limits.*` | 一个轮次内单工具和工具总调用次数                   |
| Provider 超时              | 一次模型请求                                       |
| 工具超时                   | 一次工具操作，需要在 HTTP、子进程或 MCP I/O 层生效 |
| `settings.turn_timeout`    | 整个轮次的执行预算                                 |
| HTTP 同步等待时间          | 接口等待结果的时间，不等于轮次执行时间             |

HTTP 同步等待到期后可以返回 `202` 和轮次标识，让后台继续执行；这不代表任务失败，也不代表可以取消已经产生副作用的工具操作。同一会话已有轮次执行时，应拒绝并发进入，避免两条消息同时修改同一段历史。

流式调用先聚合完整工具请求，再执行工具；不能把半段 JSON 参数直接传给工具，也不能在已经输出增量后无条件重放模型请求。

## 四、五组件怎么串成一个 Agent

以“读取 README，翻译成中文，写入 README.zh.md”为例。假设文件工具已经注册，输入和输出路径也在允许范围内：

| 迭代 | 模型返回什么                              | 运行时做什么           | 新增上下文             |
| ---- | ----------------------------------------- | ---------------------- | ---------------------- |
| 1    | 请求 `read_file` 读取原文                 | 校验路径并读取文件     | 助手工具请求与原文结果 |
| 2    | 请求 `write_file`，参数包含译文和目标路径 | 校验路径并写入文件     | 助手工具请求与写入结果 |
| 3    | 返回完成说明，不再请求工具                | 保存助手消息并结束轮次 | 最终回答               |

翻译可以在生成 `write_file` 参数时完成，不需要另安排一次只返回草稿的模型调用。模型一旦返回没有工具调用的普通回答，本轮通常就结束；如果任务要求核对文件内容，可以在写入后再次请求读取。

写入失败必须反馈错误，不能只凭模型说“已完成”就判定任务成功。

## 五、LLM 决策与 Tools 行动

模型不会直接打开文件、访问数据库或发送 HTTP 请求。模型先生成包含工具名称和参数的结构化调用意图，运行时再负责：

1. 检查工具是否在当前 Agent 的允许集合中。
2. 校验参数、权限、超时和幂等策略。
3. 执行工具并记录结果、错误和审计信息。
4. 把结果转成下一轮模型可以理解的观察结果。

`ChatModel.call(Prompt)` 和 `stream(Prompt)` 只返回模型响应，不自动执行工具请求。AgentOS 主链路由 ReActLoop 驱动，工具只经 ToolExecutor 调用统一注入的 ToolCallingManager 执行。

工具来源可以不同，但治理入口必须一致：

- 本地 `@Tool` 方法和显式回调统一为 `ToolCallback`。
- MCP 工具通过适配器转换为 `ToolCallback`。
- 注册表中的回调由 `GovernedToolCallback` 包装，处理截止时间、超时、幂等重试、结果截断、脱敏和审计。
- 内置工具在实际 I/O 前调用 Sandbox，检查路径、命令或目标端点。

`ToolContext` 用于传递 TurnContext 等应用数据，不应放进模型消息或工具 Schema；转发到 MCP 时还需去掉内部上下文。辅助 ChatClient 不携带工具，避免出现另一条执行路径。

Skill 是另一类输入：它提供方法、脚本和参考材料。ContextLoader 先注入可见 Skill 的名称、说明和路径，正文由模型通过 `read_file` 按需读取。**Skill 不是 Tool，也不会因为写进文档就自动获得执行权限。**

## 六、Memory：Agent 会不会保留状态

短期记忆是连续完成任务的基础，长期记忆用于跨会话复用事实；没有长期记忆的系统仍然可以是 Agent，只是每次会话都从零开始。

完整记录回答“发生过什么”，模型上下文回答“这次需要知道什么”，长期记忆回答“以后值得记住什么”。三者生命周期不同：

| 数据             | 保存方式与用途                                                                                | 上下文策略                                    |
| ---------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 会话、轮次和消息 | PostgreSQL 中的 `sessions`、`agent_turns`、`session_messages`                                 | 按完整轮次选择近期历史，兼顾轮数和 token 预算 |
| 长期记忆         | LongTermMemoryStore；默认 `.AgentOS/memory/MEMORY.md`，另有 PostgreSQL 与自托管 Mem0 后端设计 | 核心区全量，归档区按预算加载或检索            |
| 情景记忆         | 跨任务积累经验与过程知识                                                                      | 后续扩展，不等同于已经落库的会话消息          |

MemoryService 提供统一门面，内部委托 SessionManager 和 LongTermMemoryStore。模型上下文窗口不是数据库；从 Prompt 中裁掉旧消息，不意味着删除持久化历史。

裁剪时保留完整的助手工具请求及对应结果，失败轮次避免带入悬空工具请求。长期记忆通过 `save_memory` 写入，使用 `recall_memory` 检索，不把每句模型输出自动认定为稳定事实。

当前长期记忆包含核心区与归档区，核心区不参与截断。默认文件属于工作区级资源，不能仅凭不同 Agent 名称就推断记忆已经按用户或租户隔离。向量索引用于召回，不代替记忆本体的持久化。

## 七、Environment：能力上限与安全底线

Environment 是 Agent 所处的世界，包括文件系统、网络、业务服务、用户入口和运行凭证。工具集合决定“能做什么”，环境策略决定“能对谁、在哪里做”。

| 对象     | 必须明确的边界                                         |
| -------- | ------------------------------------------------------ |
| 文件     | 允许路径、真实路径与符号链接、读写范围                 |
| 网络     | 允许的域名和端点、连接与读取超时                       |
| Shell    | 可执行命令、参数、进程时限；解释器可绕过哪些应用层限制 |
| 凭证     | 由应用注入，不交给模型，不进入日志与工具结果           |
| 远程 MCP | 工具暴露范围、服务端权限、请求超时及内部上下文过滤     |

WhitelistSandbox 是应用层校验，不能等同于操作系统或容器隔离。MCP 工具在远端执行，也不会自动受到本地文件与命令白名单保护。运行不可信代码或服务多租户，需要更强的独立执行边界。

重试同样属于环境治理：只对确认幂等且满足策略的工具自动重试；写文件、通知或提交业务数据等操作发生超时后，要考虑副作用可能已经完成，不能把“没有收到结果”当成“没有执行”。

## 八、如何判断“它是不是 Agent”

| 对象          | 是否足以称为 Agent | 判断依据                                                 |
| ------------- | ------------------ | -------------------------------------------------------- |
| LLM           | 不足               | 它是决策组件，没有工具、环境和持续执行能力               |
| 单轮 chatbot  | 通常不足           | 没有根据反馈继续决策的自主循环                           |
| 固定 Workflow | 不一定             | 路径完全预定义时更接近确定性编排，其中可以嵌入 Agent     |
| Agent         | 可以               | 存在基于状态自主选择下一步的循环，并能通过工具作用于环境 |

判断一个系统时，先问它能否自主决定下一步，再检查 Tools、Memory、Loop 和 Environment 的边界，而不是只看产品名称。

## 九、从单个 Agent 到 AgentOS

单个 Agent 关心一次任务；AgentOS 将多个 Agent 共用的模型接入、会话、工具、调度和审计沉淀为运行底座。这里的“OS”是应用层类比：一个进程可以承载多个 Agent 定义，不要求每个 Agent 启动独立操作系统进程。

| 单个 Agent             | AgentOS                               |
| ---------------------- | ------------------------------------- |
| 关注一次任务能否完成   | 关注多个 Agent 能否稳定运行           |
| 一个上下文和一组工具   | 多 Agent 的会话、工作区和工具边界     |
| 手动配置一个模型       | Provider 映射、模型路由和调用审计     |
| 出错后查看单个日志     | 统一状态、调用记录和故障定位          |
| 直接使用本地能力       | Sandbox、权限、超时、重试和副作用治理 |
| 进程生命周期由应用负责 | 统一管理定义、触发、轮次和收尾        |

当前项目已有多模块骨架、启动与 API 规范、日志及架构检查基线；Provider、ReActLoop、MemoryService、ToolExecutor 和业务持久化链路仍需逐项实现与验收。验收至少要证明工具没有重复执行、结果可以回填、超限与取消能够停止、消息可读回、失败可追溯、越界操作被拒绝。
