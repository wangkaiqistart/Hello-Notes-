> **阅读重点**：每个模块都按“职责 → 接口 → 实现 → 验证”理解，不把代码演示误当成完整生产实现。

## 实现顺序

先建立日志、接口和模型调用的基础，再串联循环、工具和记忆，最后开放服务与扩展点。

## 模块职责

| 模块          | 关键问题                   | 验证重点                         |
| ------------- | -------------------------- | -------------------------------- |
| Provider      | 如何屏蔽模型厂商差异       | 配置映射、错误传播、模型切换     |
| ReAct         | 如何循环思考、行动、观察   | 终止条件、最大轮数、工具结果回填 |
| CLI / Channel | 消息如何进入系统           | 参数、模式复用、错误提示         |
| Notify        | 结果如何主动送出           | 通道适配、失败处理、幂等         |
| Tool          | Agent 如何真正做事         | Schema、权限、超时、结果回填     |
| Memory        | 如何跨轮次和跨会话记忆     | 读写边界、压缩、后端切换         |
| Sandbox       | 如何限制文件、Shell 和网络 | 路径、命令、资源和凭证隔离       |
| Web Service   | 业务系统如何集成           | API 契约、鉴权、统一错误和审计   |

## 工程地基

结构化日志、监控、HTTP Server、OpenAPI、代码规范和安全扫描应作为业务模块之前的共同地基。它们不直接实现 Provider、ReAct、Memory 或 Tool，却决定后续每个模块能否被定位、验证和安全交付。

### 六类基础能力

| 基础能力 | 课程中的建议 | 解决的问题 |
| --- | --- | --- |
| **结构化日志** | SLF4J + Logback，生产环境输出 JSON 和 traceId | 能按请求、轮次和工具调用追踪问题 |
| **监控** | Actuator + Micrometer + Prometheus，暴露 health 和 metrics | 能判断服务是否存活、资源是否异常、调用是否变慢 |
| **HTTP Server** | Spring MVC 配合 JDK 21 虚拟线程 | 统一 Web 入口和同步调用模型，为后续服务化做准备 |
| **API 规范** | springdoc OpenAPI、统一响应体、全局异常和错误码 | 让业务方能理解、调用和排查接口 |
| **代码规范** | Google 格式、Spotless、google-java-format、P3C 和 Checkstyle | 把格式、命名和常见 Java 规约前置到自动检查 |
| **安全检查** | SpotBugs、Find Security Bugs、PMD、OWASP 依赖扫描 | 尽早发现代码缺陷、危险调用和依赖漏洞 |

课程把这六类能力放在业务模块之前，是因为地基越晚补，跨模块返工越多。日志和指标还没有统一时，ReAct、Tool 或 Web 出问题就只能靠零散输出猜原因。

### 为什么需要项目自己的 init Skill

通用初始化 Skill 能创建基础文件，但通常不了解 AgentOS 的模块结构、constitution、命名和非协商原则。项目自己的 init Skill 应把通用工具编排成符合项目约定的初始化流程：

- 生成多模块工程骨架，并保持父 POM 和启动模块的边界。
- 安装日志、监控、HTTP、API、代码规范和安全检查。
- 把项目宪法中的关键决策映射到初始化结果。
- 让团队或社区可以重复使用同一套起步流程，减少每次新建工程的返工。

Skill 适合固化通用、可重复的流程。它负责把工具装好并按顺序执行，不能替代项目宪法、人工 Review 或持续集成。

### 初始化流程

可以把一次工程初始化拆成六个阶段：

1. **骨架**：建立 Maven 多模块、父 POM、版本管理和启动模块。
2. **日志与监控**：接入统一日志格式、traceId、健康检查和指标端点。
3. **HTTP 与 API**：配置 Spring MVC、统一响应体、全局异常和 OpenAPI 文档。
4. **代码规范**：配置格式化、P3C、Checkstyle，并明确冲突时的处理顺序。
5. **安全检查**：接入静态分析、依赖漏洞扫描和安全规则。
6. **CI 与验证**：把上述检查接入 verify 流程，启动服务并核对端点。

这六步是课程给出的施工骨架。实际项目可以调整顺序，但每一步都应留下可检查的结果，不能只在配置文件里声明工具。

### 四类职责要分开

| 角色 | 职责 |
| --- | --- |
| **init Skill** | 安装和编排基础工具，把重复初始化流程固化 |
| **constitution** | 钉死不可协商的架构、命名、安全和实现原则 |
| **CI** | 在每次变更中强制执行格式、测试、静态分析和依赖检查 |
| **Spec-Kit / 任务流程** | 在地基之上拆解并实现 Provider、ReAct、Memory、Tool 和 Web |

Skill 负责“装”，constitution 负责“定”，CI 负责“拦”，任务流程负责“做”。把这些职责混在一起，后续很难判断问题来自初始化、约束还是业务实现。

### 验收证据

工程地基至少应满足：

- Maven verify 流程可以完整执行，格式、规约、静态分析和依赖扫描有明确结果。
- Actuator health 能返回健康状态，Prometheus 指标端点可访问。
- Swagger UI 或 OpenAPI 文档可以打开并反映当前接口。
- 日志中包含可关联请求和轮次的 traceId，异常不会只打印成无法检索的文本。
- 安全检查失败时能阻止交付，或明确记录经过批准的例外。

验收重点是“工具真的生效”。只在 POM 里添加插件，不能证明工程地基已经完成。

### 课程方案与当前项目边界

课件使用 OryxOS 和 oryxos-init 作为课程阶段名称，当前知识库统一使用 AgentOS。课件中的具体工具组合、模块数量、命令和验收端点属于课程方案；是否已经接入当前项目，需要重新查看当前 POM、CI 和运行结果。

可以直接沉淀的是：先地基、后业务；用 Skill 固化重复流程；用 constitution 固定边界；用 CI 强制验证；用运行端点和扫描结果作为证据。课程中的安装步骤、依赖版本和“现场演示”属于教学内容，不自动授权当前项目执行。


## Provider：模型接入层

[Provider 原理与实现](/projects/agent-os/provider/) 介绍模型接入层的职责、Profile 加载、显式路由、请求适配、调用审计和有限重试，以及对应的验收方法。

学习时先确定三个边界：按 provider 名称选择客户端；工具执行交给 ReActLoop 与 ToolExecutor；模型调用成功和失败都留下可查询的记录。

## 重要边界

Provider 只负责调用模型，不执行工具；ReAct 只负责调度，不承载所有业务逻辑；Memory 不等于把全部历史塞进上下文；Sandbox 是安全边界，不是简单的工作目录。
